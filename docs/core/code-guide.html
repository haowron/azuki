How the design is implemented

The sections below follow the path of a message and explain which functions implement each design and how. Each section first states the design (one line), then explains the code in execution order, and ends with verbatim code excerpts (line numbers refer to commit 47b1206).

  1. Two independent processes: entry scripts, signal handling, and a shutdown order that stops intake, waits for work, then releases resources
  2. Webhook intake: shared authentication and format validation, a raw EventRequest built synchronously per provider, then publish
  3. Always-on Discord and Slack intake: prune by identity, publish the raw event, resolve the session per channel, publish before ACK
  4. Producer writes: XADD with the request JSON as the single field data; the stream id is the unique message ID
  5. Runtime reads: slot-based throttling, XAUTOCLAIM reclaims idle pending entries, over-delivered and malformed messages move to the dead stream
  6. ACK ownership: the Runtime does not ACK; the dispatch Agent ACKs explicitly at the end of processing
  7. One run per message: confirm the latest main, pin versions by name, build the Context, record start and end, turn timeouts and exceptions into results
  8. Component version store: versions are commits of the component repository, main is adopted only when it loads, pinned by name, released when unused
  9. Agent registry and LLM tiers: declared by name, built by name, resolved by name at run time
  10. The BaseAgent.run boundary and the LLM loop: Harness order, a shared step budget, parallel child agents, sequential Tools
  11. The Tool failure ledger: bucketed per agent execution, resolved per target, adjudicated at the run boundary
  12. Structured execution log: an injected LogRecorder, the parent execution fixed at start, write failures never affect execution
  13. Shared state and locks across versions: the same object by name; TaskLock is exclusive per task and not reentrant

Implementation · Two processes

The queue and the runtime are started as independent processes by their own startup scripts; they share PostgreSQL and Redis, and each handles signals and stops in its own order.

1Two independent processes: entry scripts, signal handling, and a shutdown order that stops intake, waits for work, then releases resources

Designqueue and runtime are two independent processes, each with its own event loop; execution requests pass between them only through the Redis stream. Both use run_host for signal handling, and on shutdown each first stops accepting work, then waits for accepted work, and finally releases resources.

How the code implements it

  1. scripts/start_queue.sh and scripts/start_runtime.sh change to the repository root and then run exec bash scripts/run_local.sh python -m trackeverything.api and exec bash scripts/run_local.sh python -m trackeverything.core.builtin, respectively. run_local.sh imports only the .env keys the caller has not already set (a key set to empty counts as set), exports WEBHOOK_PORT (default 18080), DATABASE_URL, QUEUE_REDIS_URL, and QUEUE_NAMESPACE, and then runs exec uv run "$@". api/app.py and core/builtin/app.py do not import each other.
  2. Both __main__.main() functions first call configure_logging() (logging.basicConfig, INFO level, one shared format) and then asyncio.run(serve()). The queue entry point also adds _ReportAccessLogFilter to uvicorn.access: after the request target is URL-decoded repeatedly, if a path segment contains reports, the target in the access log is rewritten to /reports/[redacted].
  3. api.app.serve() first calls require_schema_head(config.DATABASE_URL), then Producer.from_env(), and assembles the Connectors: github_connector() is always registered; build_discord_gateway(producer) returns a DiscordGateway only when DISCORD_BOT_TOKEN is non-empty, in which case discord_connector is registered; slack_connector(build_slack_gateway(producer)) is always registered (POST /webhook/slack always exists; the Socket Mode listener exists only when SLACK_APP_TOKEN is non-empty); schedule_connector(ScheduleTrigger(producer)) is always registered (listener only). It then enters run_host(QueueApplication(producer, connectors)) and calls producer.close() in finally.
  4. QueueApplication.start() runs in order: producer.stream.ping(); then it starts HttpServer first (when uvicorn fails to bind, _serve_http logs the SystemExit and ends the task; start() raises RuntimeError when it finds the task finished or not started within 5 seconds, so an occupied port prevents connecting to Discord and Slack); then it starts each listener in registration order. Each component is added to _started before it starts, and finally ready = True is set. If any step raises a BaseException, it calls stop() first and re-raises. /readyz returns 503 when ready is false or the Redis PING fails.
  5. core.builtin.app.serve() runs require_schema_head, prepare_runtime_environment(), load_code_version(), and recover_interrupted_runs(before=now) in order (the last closes run records that started before now and are still running as interrupted). Then build_runtime() uses open_host_services() to assemble the LLMs (max, high, low, flash), the execution log, and the session store, creates the component version store Repo and loads the mirror's main (when there is none, GitHub's main is fetched and adopted once it loads), and assembles TrackingRuntime(QueueConsumer(producer.stream), ...). prepare_runtime_state installs the Producer in queue/child.py for the child requests of components; publish_catalog writes the catalog, and then it enters run_host(runtime).
  6. Runtime.start() first calls queue.prepare() (creating the consumer group) and then creates the read-loop task; TrackingRuntime.start() then creates the maintenance tick when tick_hook exists and the interval is positive, and the component repository sync when sync_interval is positive. Every RECONCILE_INTERVAL (30 seconds) the tick runs publish_catalog and the Redis heartbeat, and every COMPONENT_FETCH_INTERVAL (300 seconds) repo.sync() fetches GitHub's main and adopts it when it loads; exceptions are only logged.
  7. run_host(app) uses loop.add_signal_handler to connect both SIGTERM and SIGINT to the same asyncio.Event, waits for that event after app.start(), always calls app.stop() in finally, and finally removes the handlers. The _HostServer used by HttpServer overrides capture_signals with a no-op, so uvicorn installs no handlers of its own and signals are handled only by run_host.
  8. The queue's stop() first sets ready = False, then stops the listeners in reverse start order: the scheduled trigger (sets the stop event and waits for the periodic task to end), Slack, and Discord stop first, and HTTP stops last (HttpServer.stop sets should_exit and waits for the serve() task to return; uvicorn then closes the listening socket and waits for in-flight connections and request tasks to finish, and the configuration does not set timeout_graceful_shutdown). Errors from the listeners are collected first and raised as an ExceptionGroup after producer.close() closes the Redis connection.
  9. The runtime's TrackingRuntime.stop() first sets _tick_stop and waits for the maintenance tick and sync tasks to end, then calls Runtime.stop(): it sets _stopping, waits for the read loop to exit, repeatedly gathers until _tasks is empty (each run ends on its own or is cut off by RUN_TIMEOUT), and then await repo.close() releases all versions; producer.close() runs in finally.
Notes
  • The code does not enforce running only one queue and one runtime against the same database (the comment in run_local.sh says so). The consumer name is fixed to runtime; when a second runtime starts, its recover_interrupted_runs closes the first process's in-progress run records as interrupted, and a second queue connects to Discord again with the same bot token.
  • Under launchd, scripts/run_service.sh supervises the queue or the runtime separately: after sending TERM to the process group it waits up to RUN_SERVICE_TERM_WAIT (default 3600 seconds) before sending KILL. When the runtime is killed, unacknowledged messages stay pending; after the next start they are reclaimed and rerun only once they have been idle for QUEUE_CLAIM_IDLE (1800 seconds), and in-progress run records are closed as interrupted at the next start.
  • The finally in serve() goes through part of the shutdown path again: the runtime calls TrackingRuntime.stop() again, where Runtime.stop() returns immediately because _started is false, and then calls producer.close() again; the queue's finally does not call QueueApplication.stop() again and only runs producer.close() once more. As a result, producer.close() is called twice in both processes.

Implementation · Queue intake

In the queue process, external input only gets format validation, is wrapped as is into an EventRequest, and is durably written to Redis Streams with XADD.

2Webhook intake: shared authentication and format validation, a raw EventRequest built synchronously per provider, then publish

DesignHTTP intake only authenticates, validates the format, and publishes the raw event; it does not interpret event contents. It returns 202 only after the XADD is confirmed, and leaves business decisions to the runtime's dispatch Agent.

How the code implements it

  1. QueueApplication.__init__ calls create_webhook_app(producer.publish, connectors=connectors, extra_routers=[...]) to create the FastAPI app (docs and openapi disabled): it first mounts /healthz and the api/ routers injected by the entry point, then registers POST /webhook/{name} for each Connector that has a webhook, raising ValueError on duplicate Connector names. Currently github (parse_github) and slack (parse_slack) are registered; Discord has only a listener and no webhook route.
  2. receive first checks the shared secret: when config.WEBHOOK_TOKEN is non-empty and the x-webhook-token request header does not match it, it returns 401. The webhook route performs only this authentication and does not verify the GitHub or Slack signature headers.
  3. When the body cannot be parsed as JSON it returns 422 (request body must be JSON); when the parsed result is not a JSON object it also returns 422.
  4. It then calls the provider's WebhookParser synchronously: parse(dict(request.headers), body) performs no I/O, and both a raised InvalidWebhookError and a pydantic ValidationError (for example, an external_id longer than 256 characters) map to 422. When the returned WebhookIntake.request is None, it returns intake.response or {"ok": True} directly with 200 and publishes nothing; Slack's url_verification returns {"challenge": ...} synchronously this way.
  5. parse_github lowercases the header names and raises InvalidWebhookError when x-github-event or x-github-delivery is missing. The payload is {"headers": ..., "body": body}: headers keeps only the non-empty entries from the allowlist _ALLOWED_HEADERS (x-github-event, x-github-delivery, x-github-hook-id), so X-Webhook-Token and authentication headers injected by the gateway are never written to Redis; external_id is the delivery ID. The entry point does not filter by event type; events such as ping are published as well, and the github agent (route_github) that dispatch delegates to decides whether to act on them.
  6. parse_slack requires event_id to be a non-empty string and uses it as external_id; the payload is the body with the top-level token removed by without_token.
  7. When there is a request, it calls await publish(intake.request), that is, Producer.publish → the XADD in RedisStream.publish; QueueUnavailableError maps to 503. After the write is confirmed, it logs webhook/<name>: queued <external_id> and returns 202 with the response body {"ok": True, "run": "queued", "message_id": ..., "accepted_at": ...}.
Notes
  • The entry point does not deduplicate by external_id: when GitHub redelivers the same X-GitHub-Delivery, a new stream message is created. For PR events, the github agent's _pr_event first reads the success record for that delivery and returns ok immediately if it exists; other events run again.
  • Only QueueUnavailableError (a wrapper around RedisError) maps to 503; other exceptions become 500. When Redis has written the entry but the response times out (client socket_timeout=5), the caller also gets 503, and a retry by the sender creates a duplicate message.

3Always-on Discord and Slack intake: prune by identity, publish the raw event, resolve the session per channel, publish before ACK

DesignThe always-on connections prune only by sender identity or by team and channel metadata, and publish the raw payload together with the session resolved from the channel mapping table, leaving content decisions to the dispatch Agent. Slack ACKs only after a successful publish; Discord buttons defer first, then publish, and report the result with a followup; the owner's Discord reactions are published raw like messages.

How the code implements it

  1. build_discord_gateway returns None when DISCORD_BOT_TOKEN is empty; DISCORD_ALLOWED_USER_ID must be a positive integer, otherwise a ValueError makes the queue fail to start; the general channel is DISCORD_GENERAL_CHANNEL, falling back to DISCORD_NOTIFY_CHANNEL when that is empty; the session resolver is open_channel_store().resolve_session. DiscordGateway creates a discord.Client with enable_debug_events=True; start() runs client.start(token) as a task on the Host loop and waits up to 30 seconds for it to become ready.
  2. discord.py has no event that hands over the raw MESSAGE_CREATE payload, so on_socket_raw_receive first filters for MESSAGE_CREATE, INTERACTION_CREATE, and MESSAGE_REACTION_ by substring, then after json.loads handles only frames with op == 0 and a dict d: the raw INTERACTION_CREATE payload is stored in _RawInteractions by interaction ID (at most _PENDING_LIMIT, that is 256, entries; the oldest is dropped when the limit is exceeded), MESSAGE_CREATE goes to _on_message, and MESSAGE_REACTION_ADD and MESSAGE_REACTION_REMOVE (_REACTION_EVENTS; the bulk removals are not among them) go to _on_reaction.
  3. _on_message prunes only by identity: it drops the message when the author is not a dict, author.bot is true, the message has a webhook_id, or the author ID differs from DISCORD_ALLOWED_USER_ID; it does not look at the content. A message that passes is published with publish(EventRequest(provider="discord", ...)), using the frame's raw d as the payload and the message ID as external_id.
  4. _on_reaction prunes only by identity: it drops the event when user_id differs from DISCORD_ALLOWED_USER_ID (the bot's own acknowledgment reactions included) and does not look at the emoji or the reacted message. An event that passes is published with the raw d as the payload, the channel's sessions from _sessions, and external_id <frame type>:<message_id>:<emoji ID or name> cut to 256 characters; a failure is only logged. The client's intents include reactions (guild and DM).
  5. _sessions(channel_id): for the general channel it returns (None, None) and binds no session; for other channels it obtains the ID of the single session that corresponds to the channel through PostgresChannelStore.resolve_session("discord", channel_id) (when none exists, it inserts a uuid4, converges with ON CONFLICT DO NOTHING, and reads again). For a thread, it finds the parent channel through the SDK-cached get_channel(...).parent_id: when there is no parent channel or the parent is the general channel, parent_session_id is None; otherwise it also resolves the parent channel's session.
  6. on_interaction handles buttons: for non-component types it discards the cached raw payload and returns; when a bot or anyone other than the allowed user clicks, it discards the raw payload and replies with an ephemeral rejection message; when the allowed user clicks, it first calls defer(ephemeral=True, thinking=True), then waits up to _RAW_WAIT (5 seconds) for the raw payload through _RawInteractions.take, publishes it with the top-level token removed as the payload and the interaction ID as external_id, and reports both success and failure with an ephemeral followup.
  7. build_slack_gateway creates a SlackGateway only when SLACK_APP_TOKEN is non-empty, and requires SLACK_TOKEN, SLACK_TEAM_ID, and SLACK_CHANNEL_ID to be non-empty. start() creates an AsyncWebClient on the Host loop; the team_id returned by auth_test() must match the configuration; it then connects a SocketModeClient with on_request as the listener. Any failure is converted to RuntimeError so startup fails; SDK logs pass through _SecretFilter, which strips tokens and drops exception details.
  8. on_request calls socket_event for events_api requests: only when team_id matches, event.channel equals the configured channel, and event_id is non-empty does it build EventRequest(provider="slack", external_id=f"{team_id}:{event_id}", payload=without_token(payload)); other requests are only ACKed. A target event first goes through publish; on failure it logs and returns without ACKing, so Slack resends it; only after success does it ACK with send_socket_mode_response(envelope_id), and an ACK failure is only logged.
Notes
  • When publishing a Discord message fails, only Discord message was not durably accepted is logged; Discord does not resend the event, so the message is lost. When publishing a button interaction fails, the user receives a failure followup and can click again.
  • If the SDK ACK fails after a successful publish, Slack resends the event. The queue does not deduplicate by external_id, and dispatch delegates the raw event to the child agent slack, so the same mention of the user may be investigated and notified again.
  • For /webhook/slack the external_id is event_id, while for Socket Mode it is team_id:event_id; also, /webhook/slack does not filter by team or channel.

4Producer writes: XADD with the request JSON as the single field data; the stream id is the unique message ID

DesignAll publishers share Producer: the request is serialized to JSON and written to the Redis Stream as the single field data; the stream id generated by XADD is the message's only ID, and the queue layer does not deduplicate.

How the code implements it

  1. Producer.from_env() reads QUEUE_REDIS_URL (default redis://127.0.0.1:6379/0) and QUEUE_NAMESPACE (default trackeverything) to create a RedisStream. The namespace must match [A-Za-z0-9_.-]{1,128}; the Redis client uses decode_responses=True, and the connect and read/write timeouts are 5 seconds. Keys are prefixed with te:{<namespace>}: the main stream is :queue, the dead stream is :dead, and the catalog hash is :catalog.
  2. The queue carries only one request model, EventRequest (extra="forbid", strict=True, frozen=True): kind has the default value event.handle, and the model carries provider, external_id, the raw payload, and an optional session. The kind of request is expressed by provider and payload: an internal payload with agent_name is a named run, and one without it starts automated development. The run ID is not generated by the publisher; the runtime issues it at execution time.
  3. Producer.publish(request) is the single publish entry point; it writes model_dump_json() directly, since the model is validated at construction. Its callers are the webhook receive, DiscordGateway, SlackGateway, ScheduleTrigger (provider="internal", with external_id set to schedule:<id>:<fire time>), publish --file in queue/cli.py (reads the file with EventRequest.model_validate_json, accepts any provider, and can republish the data of a dead stream entry as is), and three internal publishers on the runtime side.
  4. The runtime-side internal publishers are components that call publish_child(payload, key, *, session_id=None) in the Host module queue/child.py (installed with the runtime's Producer at startup), so external_id is always the current message's stream id plus :<key>: automated development (tools/issue_workflow.py) uses the key auto-start with the issue channel's session_id and a payload without agent_name; sentry_enqueue (tools/sentry/chain.py) uses sentry-item:<issue_id> with a named run of sentry_autofix_item; and the pr_retire_sweep tool, run daily by the maintenance agent, uses pr-retire:<identity>:<channel> with payload={"agent_name": "pr_cleanup", "data": {"retirement_id", "payload"}} for each closed PR that still has a recorded channel.
  5. RedisStream.publish(data) runs XADD: Redis generates the id automatically, the only field is data, and no MAXLEN is set; RedisError is wrapped as QueueUnavailableError("queue write could not be confirmed"), so the caller does not report acceptance.
  6. The stream id returned by XADD is the message's only ID: PublishReceipt.message_id is that id, and accepted_at is the millisecond part of the id divided by 1000. The runtime uses the same id as the ACK target, REQUEST_ID, AgentContext.message_id, and the task name; external_id is only part of the message content and plays no role in deduplication.
  7. The length of the main stream is controlled by ACK: RedisStream.ack runs XDEL after XACK, so only unacknowledged messages remain in the stream.
Notes
  • Publishing does not deduplicate (the docstring of Producer.publish says so): publishing the same external event twice creates two messages, which run twice.
  • When XADD has taken effect in Redis but the response times out, QueueUnavailableError is raised as well, and an upstream retry creates a duplicate. The dead stream is append-only; the code has no operation that trims it.

Implementation · Runtime reads and ACK

The runtime claims messages one at a time within the concurrency limit, checks the latest main adopted in the mirror for each message, leaves ACK to the dispatch Agent, and un-ACKed messages are reclaimed and rerun or moved to the dead stream.

5Runtime reads: slot-based throttling, XAUTOCLAIM reclaims idle pending entries, over-delivered and malformed messages move to the dead stream

DesignThe runtime limits the number of concurrently executing messages with a semaphore. Each time it gets a slot, it first reclaims pending entries that have been idle past the timeout and then reads new messages; messages whose delivery count exceeds the limit or that cannot be parsed move to the dead stream and are not executed.

How the code implements it

  1. Runtime.start() calls QueueConsumer.prepare() → RedisStream.ensure_group(): it runs XGROUP CREATE <key> runtime 0 MKSTREAM and ignores the error when the group already exists (BUSYGROUP). Both the group and the consumer name are fixed to runtime, and the start id is 0, so messages already in the stream when the group is first created are read too.
  2. _read_loop loops while _stopping is not set, and each iteration first runs await self._slots.acquire(). _slots is asyncio.Semaphore(concurrency), where concurrency comes from the RUN_CONCURRENCY environment variable, defaulting to config.RUN_CONCURRENCY (20); without a free slot it does not read Redis, so the number of executing messages never exceeds the limit.
  3. After getting a slot it calls QueueConsumer.next(): reclaim() first, and read() only when nothing can be reclaimed. reclaim() runs XAUTOCLAIM <key> runtime runtime <min_idle_ms> <cursor> COUNT 1, where min_idle_ms is QUEUE_CLAIM_IDLE * 1000 (1800 seconds); the returned cursor is stored in _claim_cursor so the next call continues the scan. When it reclaims an entry, it reads that id's times_delivered with XPENDING as the delivery count.
  4. read() runs XREADGROUP GROUP runtime runtime COUNT 1 BLOCK 1000 STREAMS <key> >, reading only new messages, with a delivery count of 1; when no new message arrives within 1 second it returns None.
  5. next() calls dead(entry, "delivered N times") for messages whose delivery count exceeds QUEUE_MAX_DELIVERIES (3), and dead(entry, "invalid message: ...") for messages that fail EventRequest.model_validate_json (including the legacy formats whose kind is agent.run or source.run); both return None and are not executed. dead() first XADDs id, data, and a reason truncated to 2000 characters to the dead stream, then runs ack (XACK plus XDEL) on the main stream.
  6. When a read fails it logs queue read failed and waits 1 second (or until shutdown); when there is no message or shutdown has begun, it releases the slot immediately and continues the loop. A message read only after shutdown begins is neither executed nor ACKed and stays pending.
  7. When it gets a message, it copies the context with contextvars.copy_context(), sets REQUEST_ID to None inside it, creates a task named trackeverything-run-<id> that runs _handle → execute, and adds the task to _tasks; when the task ends, the done callback _finished removes it from the set and releases the slot. _handle logs exceptions that escape execute (queue message %s remains pending).
Notes
  • Reclaiming looks only at idle time and does not check whether the message is still executing: RUN_TIMEOUT defaults to 3600 seconds, which is longer than 1800 seconds, so a message that has run for more than 30 minutes without an ACK is taken again by the same process and executed in parallel. The first read counts as 1 and every XAUTOCLAIM reclaim increments the delivery count, so a message runs at most 3 times and the 4th delivery goes to the dead stream.
  • Messages in flight when the process crashes or is killed, and messages read only after shutdown begins, all stay pending; XREADGROUP ... > does not redeliver pending messages, so they are reclaimed only after being idle for 1800 seconds. The reclaim cursor lives only in memory, and after a process restart the scan starts again from 0-0.
  • dead() and ack() send their commands one after another without a transaction, and the module docstring states that a failure in between is not handled: when the dead stream write succeeds but the ACK fails, the message stays pending and may later be written to the dead stream again.

6ACK ownership: the Runtime does not ACK; the dispatch Agent ACKs explicitly at the end of processing

DesignAn ACK means processing is finished and removes the message from the stream. The Runtime does not ACK; the dispatch Agent decides when to ACK, and unacknowledged messages are rerun by idle reclaiming.

How the code implements it

  1. Runtime.execute first sets REQUEST_ID to the stream id, runs await self.repo.refresh(), and then calls _run with the run handle created by repo.run(). _run puts the same id into AgentContext.message_id, sets acknowledger to self.queue.ack (QueueConsumer.ack → RedisStream.ack), and puts the run handle into agents; acknowledger takes no part in repr or comparison and never enters data, the LLM, or saved JSON.
  2. _call runs the dispatch Agent under asyncio.timeout(config.RUN_TIMEOUT); a timeout becomes a result with status="cancelled", and other exceptions become error results; exceptions raised by _run itself are also converted to _failed("execution", ...) in execute.
  3. execute calls repo.release(run) in finally and returns the result directly without calling queue.ack: whether the result is ok, error, cancelled by timeout, an unknown entrance, or a begin_run recording failure, the Runtime never acknowledges the message.
  4. Every message maps to the entrance config.DISPATCH_AGENT (dispatch) with data set to {"event": {...}}, which contains provider, external_id, and payload.
  5. DispatchAgent._execute first runs result = await self._handle(call) and then await call.ctx.ack(call.ctx.message_id). The child agents that _handle delegates to share the same ctx through call_agent and have finished before the ACK; ignored events (for example, ignored: ping), named runs (including errors such as an undeclared name), and error results returned by _handle are ACKed as well.
  6. AgentContext.ack does nothing when message_id or acknowledger is None (a run that does not come through the queue); otherwise it calls RedisStream.ack: XACK first, then XDEL, so the message leaves both the pending list and the stream.
  7. Cases without an ACK: the task is cancelled; _handle raises an exception (BaseAgent.run turns it into an error result, and the ACK in _execute does not run); dispatch exceeds RUN_TIMEOUT (named runs too); dispatch is not an entrance of the version or begin_run fails; the ACK command itself fails. These messages stay pending, are taken again by XAUTOCLAIM after 1800 seconds idle and rerun, and go to the dead stream once their delivery count exceeds 3.
Notes
  • dispatch ACKs even when _handle returns an error, so there is no retry; the failure remains only in the session's run record or the logs. A timeout cancellation does not ACK, so the message is rerun.
  • When the child agents dispatch delegated to have finished but the ACK fails, or when _handle raises after producing side effects, the whole event is rerun after 1800 seconds. For PR events, _pr_event first reads the delivery's success record and returns ok immediately for a delivery that already succeeded; other events may repeat their side effects.

Implementation · One execution inside the runtime

A message pins its versions through the run handle and is converted into an AgentContext; its start and end are recorded (runs of the same session are not serialized either), and the single entry agent, dispatch, executes it.

7One run per message: confirm the latest main, pin versions by name, build the Context, record start and end, turn timeouts and exceptions into results

DesignFor each message the Runtime starts a task in a copied context and does not interpret the content. At the start of each message it reads the mirror's main; the run handle pins each agent name to the version it first resolves to, and the Runtime directly executes the dispatch Agent from it. Each run records its start and end (runs of the same session also execute in parallel), RUN_TIMEOUT bounds the whole agent tree, every failure is returned as an AgentResult, and the dispatch Agent is responsible for the ACK.

How the code implements it

  1. Runtime._read_loop first runs await self._slots.acquire() (asyncio.Semaphore(concurrency), default config.RUN_CONCURRENCY=20, which build_runtime overrides from the RUN_CONCURRENCY environment variable), then calls QueueConsumer.next(): reclaim() first (XAUTOCLAIM, with min-idle set to QUEUE_CLAIM_IDLE=1800 seconds), otherwise read() (XREADGROUP, BLOCK 1000 ms). When there is no message, the read fails (it logs and waits up to 1 second), or shutdown has begun, it returns the slot and continues the loop.
  2. After getting (message_id, request) it copies the context with contextvars.copy_context(), sets REQUEST_ID to None inside it, and creates the _handle task with that context; the done callback _finished removes the task from _tasks and releases the slot. _handle only logs an Exception raised by execute (the log says remains pending), and CancelledError propagates unchanged.
  3. execute sets REQUEST_ID to the stream id (publish_child in queue/child.py uses it as the parent message), first runs await self.repo.refresh() (when the mirror's main has changed, it loads and switches to it in a thread; on failure it keeps the main it has already loaded), then runs run = self.repo.run() and calls _run(run, ...); any Exception raised by _run is logged and becomes _failed("execution", ...), and self.repo.release(run) in finally decrements the version's users. core does not ACK.
  4. _run does not interpret the request: the entrance name is fixed to config.DISPATCH_AGENT (dispatch), data is {"event": {provider, external_id, payload}}, request is None, and only the session and parent session from the message are carried over. Choosing the target agent and assembling the Source definition (derived by identity_for) both happen inside the run in dispatch, and the content is fetched by the child agent's fetch_source.
  5. _run generates run_id with new_id(), creates a new session_id when there is no session, and builds AgentContext(data=deepcopy(data), max_steps=self.max_steps, ...): max_steps defaults to config.MAX_STEPS (300), message_id is the stream id, acknowledger=self.queue.ack, and agents=run. acknowledger, authorization, tool_failures, tool_state, and agents are in-process fields that never enter data, the LLM, or saved JSON; the Runtime leaves authorization empty, and the dispatch Agent sets it after revalidating, before calling a child agent. The entrance's version is pinned through run.version(name), and the agent is taken from graph.agents only when the name is in that version's graph.entrances (ENTRANCES in agent/compose.py, that is, dispatch); child agents are then resolved by name through ctx.agents in call_agent, and each name is likewise pinned to the main at its first resolution.
  6. The Runtime does not serialize by session; runs of the same session also execute in parallel, and concurrency is limited only by the slots. _run first calls begin_run: in one transaction it inserts, as needed, a placeholder row for the parent session, the session row, and a session_run row whose status defaults to running, recording the original data (agents modify the deepcopy), request, and current_code_version() (inside component_scope(version.label), so it includes the entrance's version); when recording fails, no agent runs and it returns _failed("session", ...).
  7. _call returns _failed("entrance", ...) when dispatch is not an entrance of the version; otherwise it runs await agent.run(call) inside asyncio.timeout(config.RUN_TIMEOUT) (default 3600 seconds; the RUN_TIMEOUT environment variable must be a positive integer). On expiry the whole agent tree is cancelled and it returns status="cancelled" with ErrorNote("deadline", ...); other exceptions return _failed("execution", ...). _failed also writes the reason into response, because session_run stores only the response.
  8. finish_run then writes the status, response, and finished_at; a write failure is only logged and does not change the result, the row stays running, and at the next start serve() calls recover_interrupted_runs(before=...) to mark it interrupted. On external cancellation (CancelledError) it records cancelled first and re-raises, and dispatch's ACK does not run. The ACK is done by DispatchAgent._execute, which calls call.ctx.ack(call.ctx.message_id) after _handle returns; events that are not acted on are ACKed too.
  9. stop() sets _stopping, waits for the read loop to finish and for every task in _tasks to complete, and then runs await self.repo.close() to release all versions; messages read after shutdown begins are not executed and stay pending.
Notes
  • The queue tolerates a small amount of duplicate execution: a message that has run for longer than QUEUE_CLAIM_IDLE (30 minutes) without an ACK is taken again by XAUTOCLAIM while it is still running and is executed again; when a message fails before dispatch ACKs it, times out (including a named run cancelled by RUN_TIMEOUT), or the process is terminated, the message stays pending and is taken again after 30 minutes, and once its delivery count exceeds QUEUE_MAX_DELIVERIES (3) it moves to the dead stream, so it runs at most 3 times.
  • The root session_run of a named run is also recorded with agent_name="dispatch" and request=None; the child agent that actually ran appears only in the execution log. When a named run with a session (such as general) reads the conversation history, past request texts read as None.
  • Runs of the same session execute in parallel: the conversation history may be recorded in an order different from the publish order, and runs do not see each other's messages; runs for the same PR, Issue, or Source also execute in parallel, and duplicates and conflicts are accepted outcomes (see docs/components/VERSIONING.md).

8Component version store: versions are commits of the component repository, main is adopted only when it loads, pinned by name, released when unused

DesignComponents are versioned in git, and a version is a commit. The runtime reads only its bare mirror, whose main is the adopted version. With GitHub, every COMPONENT_FETCH_INTERVAL sync fetches GitHub's main and adopts it only when the current Host loads it, and the optimizer's merge pushes to GitHub first and moves the mirror's main only after the push succeeds. In local mode the mirror holds the shared main itself: people push to it from components/ through its pre-receive check, and merge fast-forwards it. The mirror's main is read at the start of each message: new runs use the new main, and runs in progress finish on their original version; a version that is not main and has no users is released immediately.

How the code implements it

  1. Versions are git commits: the version id is the 40-character SHA and the label c.<first 8>. GitVersionStore runs the git CLI against the mirror COMPONENT_REPO_DIR (default data/components.git; with GitHub, remote origin = COMPONENT_REPO_URL and deploy key COMPONENT_REPO_SSH_KEY): refs/heads/main is the adopted main (in local mode also the main people push to), refs/remotes/origin/main GitHub's main at the last fetch, and refs/te/forks/<id> the kept optimizer candidates. A version's tree is the regular files under the five folders (snapshot.owned); other files of the repository, symlinks, submodules, and caches are not part of it.
  2. A person changes components in components/ with pull → edit → push. The Host's scripts/component-hooks run the check CLI (python -m trackeverything.core.versioning check --repo <repository> <sha>) through the launcher of the checkout that holds them: a GitHub clone's pre-push for every update of refs/heads/main, and the local mirror's pre-receive for its new tip (also refusing a deletion of main). Repo.validate loads the commit with that Host's services and builds its graph without storing anything, and a failure stops the push. In local mode the runtime clones the mirror into components/ on startup when it is missing.
  3. Adopting the shared main: TrackingRuntime calls repo.sync() every COMPONENT_FETCH_INTERVAL (300 seconds). sync fetches GitHub's main (in local mode it only reads the mirror's main); when it differs from the loaded main and has not failed before, it loads it in a thread and adopts it with _advance_main (the compare-and-swap move_main(mirror main, id), then switching this process). A failed fetch or read only logs a warning and is retried; a commit that does not load is logged once at error level, recorded in _failed, and not adopted (_load_candidate, shared with refresh). On the first startup, when the mirror has no main, start fetches GitHub's main, or in local mode writes the package's default components as the root commit Initial components, and adopts it the same way; a failure aborts startup.
  4. A new version is loaded before it is kept: Repo._new_commit rejects paths outside the five folders with check_paths, writes the commit with store.write (keeping the parent's files outside the five folders; when the same commit already exists, the time moves on one second), then runs _load in a thread: loader.register, writing the read-only file view (used by __file__, Skills, and scripts), importing all modules in name order, calling the version's own agent/compose.build through the function returned by prepare_components to obtain a ComponentGraph, and setting each agent's version_label to c.<first 8 characters of the id>. Only then does store.keep create the fork ref; when any step fails, it calls _dispose and raises, leaving no ref (unreferenced objects are left to git's garbage collection).
  5. Isolation relies on the import machinery: Repo.__init__ calls loader.install(), which puts a VersionFinder that resolves only _te_versions.* at the front of sys.meta_path; for a module that is not in the version it returns None and never falls back to disk. SnapshotLoader.exec_module parses the AST from the version's source and, through OwnedImportRewriter, rewrites absolute imports that point into the four module folders to the _te_versions.v_<id> namespace; import trackeverything is bound to the version's _Facade (module folders are forwarded to this version, other names to the canonical package); importing a version-owned module with a literal import_module raises ImportError. Shared modules such as core and llm stay canonical, so all versions share the same types and locks.
  6. Merging a candidate: fork(parent, tree, message) creates a candidate without changing main. merge(id) reads the shared main R (fetching GitHub's): if R already contains the candidate, it returns main without pushing; if R is the candidate's parent, it pushes the candidate; otherwise merge_tree(candidate.parent, R, candidate) combines both changes into a new version with parent R and the message plus Rebased-From: <candidate>, loaded and validated through _new_commit. The push to GitHub never forces and the local mirror only fast-forwards (PushRejected when another push landed after the read), and the mirror's main moves only after that succeeds; MergeConflict, GitError, and load failures likewise leave the mirror's main unchanged.
  7. Reading main: Runtime.execute calls refresh() first for every message; when the mirror's main equals the one already loaded it returns immediately without taking the lock, and otherwise it loads and switches to the new main (a main that sync adopted in this process is already loaded and switched). When loading fails, it records the id in _failed, logs it once through describe_failure, and keeps using the main it has already loaded.
  8. Pinning by name: the RunVersions returned by repo.run() is put into AgentContext.agents. The first time version(name) is called it records the current main, and afterwards that name always returns this version within the same run; each version increments users only once. The Runtime uses it to get the entrance, and BaseAgent.call_agent and _build_callables use it to get child agents. During execution, current_code_version() carries the running agent's own version_label.
  9. Release: when a run ends, Repo.release(run) ends the run's use (RunVersions.end decrements the users), and _collect releases every version that is not main and has 0 users; when main switches, the old main is also released immediately if it has no users. _dispose unregisters the loader, removes the namespace's modules from sys.modules, the attributes on the root package, and the linecache entries, clears the component graph, and deletes the file view (a directory that fails to delete is retried at the next release); the commits stay in the mirror.
Notes
  • Global variables of version-owned modules exist once per version; locks and caches that must be unique across versions use shared_state (see the section on shared state across versions); releasing removes only the version's own references and does not touch shared objects.
  • The runtime does not watch files or read a checkout: a person's push reaches the runtime only through sync, and a deploy of this repository never changes components.
  • Host changes (core/, llm/, and so on) take effect when the supervisor restarts; when the new Host contract is incompatible with the adopted main, the runtime refuses to start. Deploy such a change in a form the current components still load with, then push the components (the pre-push hook checks against the deployed Host); to recover, push a main that loads and point the mirror's refs/heads/main at it.

9Agent registry and LLM tiers: declared by name, built by name, resolved by name at run time

DesignChild agents and LLMs are both declared by name. The Host provides only the LLM clients named max, high, low, flash, and flash_low, and the version's agent/compose.py passes the list of agent classes to build_agents, which builds exactly one instance per name and validates child agent names, so composition errors fail while the version is loaded; child agent instances are not bound, and are resolved by name through the run handle at run time.

How the code implements it

  1. BaseAgent declares its composition with class variables: name; llm (default max, a key of HostServices.llms); agents (a tuple of child agent names); tools, pre, post, on_error (tuples of types); fatal_tools; hidden_callables. For example, PrEventAgent declares llm as flash_low and agents as (*DiscordOutputAgent.agents, "project_memory", "review", "pr_cleanup", "document"), and ProjectAgent declares llm as flash.
  2. BaseAgent.__init__(llm, *, logger) instantiates the declared Tools with no-argument constructors and the Harnesses with the same llm, and registers them one by one (_add_unique rejects duplicate names with ValueError); it neither creates nor binds child agents (agents is deduplicated and stored as _agent_names), and it never replaces the LLM while running.
  3. On the Host side, open_host_services calls build_llms(logger): it creates one asyncio.Semaphore(config.LLM_CONCURRENCY) (default 10) and wraps every client as TrackedLLM(ThrottledLLM(inner, sem), logger). max comes from build_default_llm(): with ZAI_API_KEY it is a z.ai reasoning client with effort max (wrapped in FallbackLLM when DEEPSEEK_API_KEY is also set); otherwise it is DeepSeek, then OpenAI, and when neither is available it raises RuntimeError. With ZAI_API_KEY, high and low are z.ai clients with the corresponding effort, and flash and flash_low are GLM-5.3-Flash (config.ZAI_FLASH_MODEL) clients with effort high and low; otherwise they are the same object as max. The result goes into HostServices(llms=..., logger=..., session_store=..., full_mesh=..., skills_root=...).
  4. The prepare(version) returned by prepare_components(services) takes the version's trackeverything.agent.compose and calls build(services, skills_root=...); agent/compose.build calls build_agents with the AGENTS tuple, services.llms, services.logger, and the per-name constructor dependencies (history for project_qa and general; sources for dispatch and github).
  5. The first phase of build_agents builds class by class: a class without name, a duplicate name, or a cls.llm that is not in llms raises ValueError; each class that passes the checks is built once with cls(llms[cls.llm], logger=logger, **extra.get(cls.name, {})). It then checks whether the constructor dependencies mention any name that was not built.
  6. The second phase only validates names: when any name in a parent instance's list_agent_names() is not in the set of built agents, it raises ValueError. It binds no instances and does not propagate the logger (every instance gets the same logger from its constructor arguments); each name has exactly one instance, and circular declarations also pass validation.
  7. agent/compose.build then registers one shared FetchSourceTool(dict(SOURCES)) on every instance whose fatal_tools includes fetch_source, and registers shared instances of the base tools (BASE_TOOLS) on all instances; when AGENT_FULL_MESH is on it calls wire_full_mesh(agents) (extend_callables adds only undeclared Tools and child names and skips the agent itself), then binds the Skill catalog with bind_skills(agents, ...), and returns ComponentGraph(agents=agents, entrances=frozenset(ENTRANCES), sources=dict(SOURCES)).
  8. Any ValueError during building is a failure to load the version: sync does not adopt that version, fork keeps no fork ref, the check CLI fails, a failure to load main at startup aborts startup, and a refresh failure keeps the current main. At run time, child agents can be called only through call_agent: it resolves the instance by name through ctx.agents, and when the name is not a declared child or cannot be resolved it returns an error result with ErrorNote("delegation", ...).
Notes
  • An agent instance is shared among all parent agents and all runs of the same version, and so are its instance attributes (such as the _channel_store that DispatchAgent creates lazily); per-run state lives in AgentContext or in the call scope AgentToolScope. Agents with the same name in different versions are different instances.
  • ComponentGraph.agents contains all agents of the version, but entrances contains only ENTRANCES (dispatch): the Runtime always executes dispatch, and other agents can be reached only as child agents. dispatch declares 17 child agents in the agents tuple of agent/dispatch.py (github, general, project_qa, issue, pr_event, ci_failure, issue_investigation, issue_cleanup, project_memory, review, document, slack, pr_cleanup, sentry_autofix, sentry_autofix_item, optimizer, and reservation_fire): event routing hands GitHub events to github (which further routes them to pr_event, ci_failure, issue_investigation, or issue_cleanup), Discord messages to project_qa, issue, or general, Discord confirmation buttons to general, Slack events to slack, and auto-development internal events to issue; a named run can specify any of these names (an agent_name of discord runs as a general conversation); when a name not in this list (such as triage) is given as the agent_name of a named run, dispatch runs no child agent, ends with an error, and ACKs.
  • When ZAI_API_KEY is not configured, high, low, flash, flash_low, and max are the same object, so an llm declaration never makes building fail; all tiers share the same Semaphore, so the LLM concurrency limit applies to the whole process.

10The BaseAgent.run boundary and the LLM loop: Harness order, a shared step budget, parallel child agents, sequential Tools

DesignBaseAgent.run is an agent's only execution boundary. It runs pre, _execute, post (only on ok), and adjudication in that order, and only cancellation propagates outward. The LLM only returns an answer or calls; BaseAgent decides when to stop, whether a call targets a Tool or a child agent, and whether calls run in parallel or in sequence.

How the code implements it

  1. run is @final: it first creates an agent-type _Span (its request is a snapshot of request and ctx.data), then _enter sets four ContextVars, current_run_id, current_agent_execution_id, current_parent_agent_execution_id, and _current_scope (plus current_component_version when the instance has a version_label); AgentToolScope.depth is the outer depth plus 1 (1 for the entrance), and they are restored in reverse order in finally.
  2. When the depth exceeds MAX_AGENT_DEPTH (16), it raises RuntimeError without running the pre Harnesses or _execute, and this becomes an error result directly. Otherwise it runs await self._check_pre(call) or await self._execute(call): pre Harnesses are evaluated in declaration order through _evaluate, an exception raised by a check counts as a rejection (fail-closed), and the first rejection returns an error result with ErrorNote("harness:<name>", ...) without running _execute.
  3. Post Harnesses run only when status == "ok", and the first rejection replaces the result (the harness log keeps original_result); then _adjudicate adjudicates unresolved Tool failures. On CancelledError it takes and discards the failures, records cancelled, and re-raises; other exceptions become an error result with ErrorNote("execution", ...) plus the failures taken. Finally it writes the agent log, and on error it runs the on_error Harnesses in order, whose failures are only logged.
  4. The default _execute calls _execute_llm_loop: _build_messages produces the system message (get_prompt()) and the user message (JSON of request and data), and _add_system_extras(messages, ctx) appends the Skill catalog once to the end of the first system message, plus PARALLEL_CALL_RULE when the callables include child agents. In each round, _build_callables(ctx) lists the Tools and the child agents resolved through ctx.agents, minus the hidden_callables merged along the MRO (hidden children are not resolved).
  5. _respond_one_step first calls ctx.advance_step(): there is no await between the check and the increment, so a single event loop never overshoots; the same AgentContext is shared by the whole agent tree, so the budget (the max_steps given by the Runtime) belongs to the whole tree. When the budget is exhausted it returns None, and the loop ends with max_steps. A FinalAnswer returns ok (or enters the repair path); for Calls, the call JSON and raw are first appended as an assistant message and then handed to _dispatch_calls, and the observations are appended as tool messages.
  6. _dispatch_calls processes calls in order: a name that was not offered to the LLM in this round is not executed; it writes a tool log entry and returns callable was not offered; a call that resolves to no Tool but belongs to a child agent is collected into a group; for a Tool call, it first runs the accumulated child agents with _run_children and then runs the Tool on its own. At the end it runs the remaining group, and the observations are returned in call order.
  7. _run_children runs a single child agent in the current task and runs several in parallel with asyncio.TaskGroup. _dispatch calls call_tool(ctx, LLMCall(name, tool.llm_args(args))) for a Tool and call_agent(agent_call, name, args.get("request")) for a child agent; the observation contains status, output, and the rendered errors.
  8. call_agent is @final, and both LLM calls and Python control (such as DispatchAgent._delegate) go through it: it resolves the child instance by name through call.ctx.agents, and when the name is not a declared child, there is no run handle, or it cannot be resolved, it returns an error result with ErrorNote("delegation", ...); otherwise it runs child.run(call.child(request)), where the child call references the same AgentContext. Child agents in hidden_callables can be called this way too.
Notes
  • Parallel child agents share the same ctx.data, tool_state, authorization, and step counter; dependent calls must go into later responses, and PARALLEL_CALL_RULE tells the LLM this rule.
  • The child tasks in a TaskGroup copy the same context and share the parent agent's version pins in ctx.agents; agents hold no locks, and no agent is called while a Tool holds a lock, so a parent agent never holds a lock while waiting for a child agent.
  • The step budget limits only LLM rounds; it does not limit the Tool and child agent calls made by Python control, and LLM calls inside external CLIs are not counted either.

11The Tool failure ledger: bucketed per agent execution, resolved per target, adjudicated at the run boundary

DesignAll Tool side effects go through call_tool(); a failure becomes a ToolResult and is recorded in the shared Context's ToolFailures, and a later success on the same target resolves it. Each agent takes its unrecovered failures at its own run boundary, and only failures of fatal_tools turn ok into error.

How the code implements it

  1. AgentContext.tool_failures is a ToolFailures() with init=False, and never enters repr, the LLM, or saved JSON. _entries is bucketed by current_agent_execution_id.get(); BaseAgent._enter sets this ContextVar for each agent execution, so although the whole tree shares one Context, every agent execution (including each child agent) has its own bucket.
  2. call_tool executes through _invoke: when the name resolves to no Tool, the result is ToolResult(ok=False, error="unknown tool: ..."); a Tool that comes from a Skill first runs that Skill's definition check; an Exception raised by a Tool becomes ToolResult(ok=False, error="<type>: <message>"); CancelledError only writes a cancelled log entry and propagates, without entering the ledger.
  3. The target key is tool.error_key(call.args) (None when the Tool does not exist). On success it calls resolve(name, key); on failure, record(name, key, ErrorNote(name, error or "tool failed")). A slot is formed from the Tool name and the key, using * when the key is None; resolve removes both the matching slot and that Tool's * slot, so at any time the ledger holds only unrecovered failures.
  4. Tool.error_key defaults to the arguments as key-sorted JSON, so only a successful retry with the same arguments resolves a failure; Tools with narrower targets override it, for example project_edit_doc, project_create_doc, and project_delete_doc use store.doc_error_key(args). ErrorNote.stage is the Tool name, so fatal_tools is checked against note.stage.
  5. _adjudicate calls take() at the run boundary to take and delete the current agent execution's bucket: an ok result with fatal failures becomes error, with errors set to those fatal notes; an ok result without fatal failures is unchanged, and the other failures appear only in the error field of the agent log; for a non-ok result, errors is the existing notes plus the fatal notes, and when it is still empty, max_steps adds ErrorNote("budget", ...) and other statuses add a note whose stage is the agent name and whose reason is the response, so every non-ok result has at least one note.
  6. The exception path puts ErrorNote("execution", ...) into errors together with the failures taken by take(); the cancellation path calls take() and discards the result. A child agent's failures are taken at its own boundary and reach the parent as the status and errors returned by call_agent, and a child agent's success cannot resolve failures in the parent's bucket either.
  7. _execute_llm_loop(call, repair_tool_failures=True) (used by ProjectAgent and GeneralAgent) checks ctx.tool_failures.unresolved(*self.fatal_tools) when the LLM gives a FinalAnswer: when there are unresolved fatal failures, it keeps that answer and appends the assistant's text once, plus a user message with _REPAIR_PROMPT and the notes, so the LLM can repair them and give the complete answer again; when they are still unresolved at the next answer, or unresolved fatal failures remain when the budget runs out, it returns _incomplete (error whose response is the latest answer, or a list of the unfinished operations when no answer was given), and _adjudicate then attaches each fatal note once.
Notes
  • A non-ok result merges only fatal failures: advisory failures enter neither errors nor the error field of the agent log, and remain only in the error of their own tool log entries.
  • With the default error_key, a successful retry with different arguments does not resolve an earlier failure; Tools that need per-target resolution must override error_key, and a failure whose key is None is resolved by any success of the same Tool.
  • call_tool calls made directly by Python control (such as ProjectAgent reading the document list) go into the same bucket as LLM-initiated calls and take part in adjudication in the same way.

12Structured execution log: an injected LogRecorder, the parent execution fixed at start, write failures never affect execution

DesignEach execution of an Agent, Harness, Tool, or LLM, and of the PR review CLI (review_pr), is written as one LogEvent when it ends (other external CLIs appear only in the tool event that calls them); parent-child relationships are determined by ContextVars at the start of the execution, and the events within a run share a run_id; a log write failure is only logged and does not change the execution.

How the code implements it

  1. core/abc/execution_log.py defines only the LogRecorder protocol (async record(event)); LogEvent and the four ContextVars current_run_id, current_agent_execution_id, current_parent_agent_execution_id, and current_component_version live in core/builtin/domain/execution_log.py. open_host_services opens one PostgresExecutionLogger with open_execution_logger() and hands it to both build_llms(logger) and HostServices.logger.
  2. Injection on the agent side: build_agents passes the same logger to every constructor, and the logger is not propagated between parent and child. _log writes only when self._logger is not None.
  3. _Span generates execution_id when it is created, takes parent_id from current_agent_execution_id.get, and records started_at and elapsed_clock() (CLOCK_MONOTONIC_RAW on macOS, CLOCK_BOOTTIME on Linux, including system sleep time); end() copies the request, result, and error with snapshot() to build the LogEvent.
  4. Agent events: run creates the span before _enter, so the parent execution is the calling agent's execution (None for the entrance); _enter then sets this execution_id as current_agent_execution_id and sets current_run_id, the parent execution ID, and (when the instance has a version_label) current_component_version. At the end it writes the status (ok, error, max_steps, cancelled), and the error field holds the notes produced by adjudication.
  5. Spans created within the same agent execution all have it as their parent: harness events have the component harness:<Agent>.<Harness>; pre records ok or blocked, post records ok or rejected (with original_result), and on_error records ok or failed; tool events are written by call_tool as ok, error, or cancelled, and a call that was not offered to the LLM writes one error.
  6. LLM events are written by TrackedLLM.respond, the outermost wrapper of every client, independent of agents: run_id comes from current_run_id (newly generated when absent), and the parent execution from current_agent_execution_id; on success the component is <provider>/<model>, the result is final_answer or calls, and usage plus the cost_usd computed by calculate_cost_usd are attached; on an exception it records component llm with status error and re-raises. ThrottledLLM is the inner layer, so duration_ms includes the time spent waiting for the Semaphore.
  7. CLI events are written by _log_cli in tools/review.py: it calls open_execution_logger() itself, the component is review_pr, run_id comes from ctx.run_id (- without a ctx), the parent execution from current_agent_execution_id, and the result contains measurements such as the CLI version, the model, and the exit code; a recording failure only calls log.warning.
  8. PostgresExecutionLogger.record inserts each event into the logs table through the ORM with a short-lived session, and writes code_version=current_code_version() (during an agent execution, <Host version>+c.<first 8 characters of that agent's version id>); any exception goes to log.exception and is swallowed. snapshot() itself never raises; values that cannot be serialized are recorded as snapshot_error and repr. On the read side, api/runs.py turns events into steps with id and parent, and an agent event whose parent_execution_id is None is the root of the run.
Notes
  • Events are written only when an execution ends; when the process is forcibly terminated, in-progress executions have no events, and the corresponding session_run rows are marked interrupted at the next start.
  • The tasks of parallel child agents copy the context when they are created, so the parent execution of each child agent in a TaskGroup is still the agent that made the call.
  • When an LLM is called outside an agent (no current_run_id), the LLM event gets a newly generated run_id and is not associated with any run.

13Shared state and locks across versions: the same object by name; TaskLock is exclusive per task and not reentrant

DesignLocks and caches that must be unique across versions stay in component modules and are obtained by name from the Host's process-wide container through shared(), task_lock(), and keyed_lock(); a lock wraps only a single operation inside a Tool, is exclusive per task, and is not reentrant: when the holding task requests it again, it fails immediately instead of waiting for itself.

How the code implements it

  1. shared(name, factory) caches by name in the global dict _objects, guarded by _guard, a threading.Lock: the first call runs the factory, and afterwards every version gets the same object. When the module of the value's type starts with _te_versions. it raises TypeError, because instances of version-owned classes would keep old version code alive and isinstance would split by version; the check is shallow and looks only at the value itself. Releasing a version does not clear this container, and objects live until the process ends.
  2. context_var(name, default) and task_lock(name) are convenience functions built on shared; the Discord send lock and channel cache, the Gmail token, and the pending lock of tools/fix use task_lock or shared.
  3. TaskLock.hold() must run in a task: when the holder is the current task, it does not wait and immediately raises RuntimeError (not reentrant, so the same task never waits forever for itself).
  4. Otherwise, when the internal asyncio.Lock is unlocked and belongs to a different loop, it is replaced with a new lock for the current loop; after acquire it records the holder, and on exit it clears the holder and releases; other tasks wait on acquire. It does not recognize parent-child relationships between tasks.
  5. keyed_lock(namespace, key) takes or creates the TaskLock for (namespace, key) under _guard and increments its user count, decrementing it in finally; when the last user (including waiters) leaves, the key is deleted, so keys do not grow without bound.
  6. Only Tools in versions use these (the Host calls no component module): the Discord send lock, channel lock, and ensure lock, the Gmail token lock, and the pending lock of tools/fix use task_lock, and issue_lock in tools/issue_workflow.py (that is, keyed_lock("issue", key)) wraps the channel decision and record in _ensure_channel, and, in _close of Issue close, the check and update of the development record, the deletion of the dedicated Discord channel, and the clearing of the source links. The Runtime and agents such as dispatch, pr_event, issue, the Issue engineering flow, project_memory, and project hold no locks, and runs for the same session, PR, Issue, or Source execute in parallel.
  7. Lock rule: a lock wraps only a single operation inside a Tool and no agent is called while it is held, so a lock is never held while waiting for a child agent. The file locks in tools/project/locks.py (the project commit lock and the exclusive file lock used by the work docs store) work across processes and register their holders with shared; a second acquisition by the same task is allowed to reenter as nesting within a Tool (document reads during a commit, manual arbitration, or notification recording).
Notes
  • These objects are shared only within one process; they are not persisted and are not shared between the queue and runtime processes, so values needed after a restart belong in files or a Store. A TaskLock inside a Tool is therefore mutually exclusive only within a single process; cross-process exclusion uses the file locks in tools/project/locks.py.
  • shared() checks only the value itself: version-owned instances placed inside a container are not rejected; when the shape of a value changes, use a new name.
  • TaskLock is not a thread lock: it targets tasks on the same event loop, and the internal asyncio.Lock moves to a new loop only when it is unlocked.
  • The agent layer has no exclusion per business unit: review, comment handling, and docs sync for the same PR may overlap, and investigation, engineering progress, and Codex execution for the same Issue may overlap or write to the same workspace directory at the same time; project sync tries an optimistic commit at most _ATTEMPTS (3) times and fails when every attempt is stale.

Rules it follows

  • run is @final; control changes go only in _execute (and hooks such as _build_messages and get_prompt). An Exception raised by the depth limit, _execute, or _adjudicate is converted to an AgentResult with status="error", whose errors are the execution note plus all of this execution's unresolved Tool failures. Exceptions raised by the check of a pre/post Harness do not take this path: _evaluate catches them and treats them as refusals, so the result has a harness:<name> note (cause failed closed: <type>: <message>) and no execution note.
  • asyncio.CancelledError discards this execution's unresolved failures, records an agent event with cancelled, and re-raises; the on_error Harnesses do not run.
  • The execution order is fixed: depth check → pre → _execute → post (ok only) → _adjudicate → record the agent event → on_error (only when status == "error"; max_steps does not trigger it). Each Harness chain is evaluated in class declaration order, then in register_*_harness order, and short-circuits on the first refusal. An Exception raised by a pre or post check counts as a refusal (fail-closed); a failure of on_error itself only records a failed event and a warning log and does not replace the original result.
  • A non-ok result carries at least one ErrorNote: when there are no notes, max_steps gets a budget note and anything else gets a note whose stage is the agent name. Callers read errors instead of parsing response.
  • The Tool failure ledger is slotted by current_agent_execution_id; a child agent's Tool failures are consumed at the child's run boundary and do not enter the parent agent's arbitration. fatal_tools matches on ErrorNote.stage (the Tool name written by call_tool).
  • Consecutive child agent calls in one response run in parallel, and a Tool call waits for the preceding child group to finish and then runs alone; observations are returned in request order, and names that were not offered are never executed. A child agent's failure is returned as an AgentResult and does not cancel the other children in the group through the TaskGroup.
  • Child agents run only through call_agent; the child call is created by call.child(request) and shares the same AgentContext (data, step budget, failure ledger). When the LLM delegates to a child agent, only the request from the arguments is passed to the child.
  • The Context never goes into JSON arguments: on the LLM path the arguments are converted by Tool.llm_args, and call_tool injects ctx into Tool.run as a keyword.
  • Child agent instances are not bound at composition: call_agent, child_meta, and _build_callables obtain them by name through ctx.agents each time, and within one run the run handle fixes a child agent of a given name to the version obtained first. Children offered to the LLM are obtained when the callables are built; children in hidden_callables are not obtained until they are called.
Pitfalls
  • hidden_callables is merged from vars(cls) of each class in type(self).__mro__, so a subclass writes only its own additions. Hidden names do not appear in the callables, so an LLM call gets callable was not offered, while Python control can still call them through call_agent or call_tool.
  • Skill Tools added by register_run_tools belong only to this execution's scope whose owner is self; a child agent's run creates a new scope and cannot see the Skill Tools loaded by the parent execution. offered is computed at the start of each step, so calling a new Tool after read_skill in the same response counts as not offered; it becomes available from the next LLM call.

builtin/runtime.pyTransport-independent execution infrastructure in the runtime process: reads execution requests from the queue one at a time and runs the dispatch agent directly on a run handle for the latest main adopted in the mirror; the Runtime does not ACK.

runtime185 linesView source

Runtime.start first runs await queue.prepare() so the consumer group is ready, then starts the read loop _read_loop. Each iteration of the loop first acquires a slot of asyncio.Semaphore(concurrency) and then calls queue.next(); once it gets a message, it sets REQUEST_ID to None in a context copied with contextvars.copy_context() and creates a _handle task, and _finished returns the slot when the task completes. execute sets REQUEST_ID to the stream id during execution, first runs await repo.refresh() (loading the new version if the mirror's main changed), then creates a run handle with repo.run() and calls _run, and at the end (success, failure, cancellation, or timeout) calls repo.release(run) in finally. The Runtime itself does not ACK; the dispatch agent does it through ctx.ack. _run does not interpret the request content: the entrance is fixed to config.DISPATCH_AGENT (dispatch), run.version(name) pins the entrance name to the current main, data is {"event": {provider, external_id, payload}}, request is None, and the session and parent session come from the message (a new session is created when absent). It then generates run_id, builds an AgentContext with max_steps, message_id, acknowledger=self.queue.ack, and agents=run, takes the entrance instance only when the name is in the version's graph.entrances, and runs begin_run, _call, and finish_run in order inside component_scope(version.label), so that session_run carries the entrance version's code_version. Runs are not serialized per session; runs of the same session also execute in parallel. _call wraps agent.run in asyncio.timeout(config.RUN_TIMEOUT), converts a timeout to cancelled, and converts a missing entrance (unknown entrance) and exceptions to an error result. stop stops reading, waits for all running tasks to finish, and then runs await repo.close(). Reclaiming, the delivery limit, and the dead stream are not in this module; they are handled by QueueConsumer.next in queue/consumer.py and RedisStream.reclaim/dead in queue/redis_stream.py. Choosing the entrance, assembling Source definitions, and interpreting events per business object are the dispatch agent's job, and the Runtime does not reference Sources.

UsageSits between the queue and the agents: takes an EventRequest from QueueConsumer, converts it to an AgentCall, and calls the dispatch agent in the version pinned by the run handle; at the end it records the session_run and releases the run handle. ACK is performed by the dispatch agent.

Rules it follows

  • The number of messages executing at once never exceeds concurrency: a slot is acquired before reading the queue, and it is returned immediately when no message is obtained or a message is read after stopping.
  • Each message runs on the mirror's main as of the start of the run: the run handle created after refresh pins each agent name to the main obtained first, so an agent with a given name does not switch versions within one run; after main switches, runs in progress finish on their original version. Tasks start in a copied context where REQUEST_ID is first set to None and then set to this message's stream id during execution.
  • Runs of the same session_id also execute in parallel, and the number of concurrent executions is limited only by concurrency. The agent is called only after begin_run succeeds; on failure the agent does not run and an error at the session stage is returned.
  • The Runtime does not ACK; messages are confirmed only by the dispatch agent's ctx.ack. When the run is cancelled (CancelledError), execute raises, or dispatch ends before the ACK, the message stays pending.
  • A timeout result is status="cancelled" with ErrorNote("deadline", ...); the Runtime does not retry, and finish_run records the result as usual.
  • A failure of finish_run is only logged and does not change the returned result; the row stays running and is closed as interrupted by recover_interrupted_runs in app.serve at the next startup.
  • The run handle is released in the finally of execute: whether the run ends in success, failure, cancellation, or timeout, the version's user count goes down, and a version that is not main and has no users is released immediately. The code_version of session_run is <Host version>+c.<first 8 chars of the entrance version id>.
  • Shutdown order: set the stop event → wait for the read loop → wait for all tasks → repo.close().
Pitfalls
  • stop does not cancel running tasks. Each run's agent execution is bounded by RUN_TIMEOUT (default 3600 seconds), but begin_run and finish_run do not count toward that deadline, so the drain time can exceed RUN_TIMEOUT.
  • Reclaiming is done by RedisStream.reclaim with XAUTOCLAIM based on the idle time QUEUE_CLAIM_IDLE (1800 seconds), and the consumer name is fixed to runtime. A message still un-ACKed after more than 1800 seconds of execution is reclaimed again by the same process and runs in parallel with the original execution (even with the same session_id), and the default RUN_TIMEOUT is longer than that idle time.
  • If a message ends before the dispatch agent reaches ctx.ack (an exception, a RUN_TIMEOUT timeout, or dispatch not being in main's entrances), it stays pending, is reclaimed after 1800 seconds, and runs again; once the delivery count exceeds QUEUE_MAX_DELIVERIES (3), QueueConsumer moves it to the dead stream. A named run cancelled by RUN_TIMEOUT is likewise run again.
  • When runs of the same session execute in parallel, the conversation history may be recorded in a different order from the publish order, and the runs cannot see each other's messages.
  • When begin_run fails, dispatch does not run, the message is not ACKed, and it is reclaimed and retried after 1800 seconds of idle time.
  • The Runtime starts only config.DISPATCH_AGENT: graph.agents contains all of the version's agents, but only names in graph.entrances can serve as entrances. A named run can reach only child agents declared by dispatch; for an undeclared name, dispatch returns error and ACKs.
  • The root session_run recorded by begin_run always has agent_name="dispatch" and request=None, including for named runs; when a named run with a session (such as general) reads the conversation history, past request text reads as None.
  • Messages that were read but not executed before shutdown are reclaimed only at the next startup, after more than 1800 seconds of idle time.
  • When refresh fails to load a new main, it logs only once and later messages keep using the already loaded main; a failure to read the mirror's main likewise keeps the current one without failing the run. refresh and repo.run() sit outside the inner try of execute, so a RuntimeError such as a closed version store is logged by _handle and the message stays pending.

versioning · component versions

Reads versions from the component repository, adopts main, and resolves Agents by name. core/versioning is the component version store. Components (agent/, tools/, skills/, harnesses/, sources/) are versioned in git, and a version is a commit (version id = the 40-character commit SHA, label c.<first 8>). People work in the working copy components/ and push to the shared main: the component repository on GitHub (COMPONENT_REPO_URL) or, in local mode, the mirror itself, whose first main is the package's default components. snapshot defines the five version-owned folders, which paths belong to a version, the path checks of a new tree, and logical module names. store defines Commit, the VersionStore Protocol, and its git implementation GitVersionStore, which reads and writes the bare mirror COMPONENT_REPO_DIR (refs/heads/main = the adopted main, refs/remotes/origin/main = GitHub's main at the last fetch, refs/te/forks/<id> = optimizer candidates) and, with GitHub, fetches from and pushes to its main; in local mode fetch reads the mirror's main, push fast-forwards it, and initial_tree gives the package's default components for the first main (the two modes are the internal strategies _GitHubUpstream and _LocalUpstream); the function ensure_working_copy clones the mirror into components/. loader loads the source of the version's 4 module folders into the reserved namespace _te_versions.v_<version id> and rewrites owned absolute imports, so old and new versions coexist. OWNED is the five folders agent, tools, skills, harnesses, sources, and MODULE_FOLDERS the 4 of them loaded as modules (.py files under skills/ and every other file are resources). skipped decides that a path is never part of a version (__pycache__, a segment starting with ., .pyc); owned decides that a path of the component repository belongs to a version (under one of the five folders, at least two segments, and not skipped), so files at the repository root such as README.md and .githooks/ are not part of a version. check_paths raises ValueError for keys of a new tree that are absolute paths, contain empty segments, ./.., or backslashes, or are not under the five folders. package_tree reads the regular files of a package's five folders (the first local main). logical_name maps a .py under MODULE_FOLDERS whose segments are all identifiers to a logical name (agent/review.py → trackeverything.agent.review), and module_path is its inverse; index_modules builds a version's ModuleIndex (logical name → source, packages with source, and intermediate packages without source), raising ValueError for non-UTF-8 modules. It uses no git, hashing, or file system.

UsageGitVersionStore uses owned to select a commit's files and OWNED to keep the parent's files outside the five folders when writing; Repo._new_commit and Repo.validate call check_paths; Version uses logical_name to tell modules from resources, and loader uses MODULE_FOLDERS and module_path to find the origin on the file view.

Rules it follows

  • A version's tree contains only paths for which owned is true; keys are POSIX paths relative to the repository root (equal to paths relative to src/trackeverything), and the first segment is always one of OWNED.
  • The module/resource distinction depends only on the path: a .py under MODULE_FOLDERS with identifier segments is a module, everything else is a resource.
Pitfalls
  • Empty folders do not enter a tree (git does not store them); a folder containing only skipped files is treated as nonexistent.
  • A .py in MODULE_FOLDERS whose name contains a non-identifier segment has a logical_name of None and is loaded as a resource, not a module.
  • Non-UTF-8 module files are not detected here; they fail at Version construction with ValueError (<relative path>: not UTF-8).
  • check_paths applies only to trees the Host writes or validates (forks, rebased merges, the check CLI); a commit pushed by a person is filtered by owned instead, so its files outside the five folders are ignored rather than rejected.

versioning/store.pyDefines Commit, the value of a stored version, the errors GitError and MergeConflict, the VersionStore Protocol of the storage side, and its git implementation GitVersionStore, which reads and writes the runtime's bare mirror. Where the shared main lives is a strategy: _GitHubUpstream fetches from and pushes to the component repository on GitHub, and _LocalUpstream keeps the shared main in the mirror itself, seeded from the package's default components. ensure_working_copy clones the local mirror into people's working copy.

runtime438 linesView source

A version is a git commit, and its id is the 40-character commit SHA. Commit is a frozen, slots dataclass (id, parent = the first parent, message, created_at = the committer time in whole seconds). All VersionStore methods are coroutines: read_main and move_main(expected, new) (the mirror's adopted main; compare-and-swap, never touching GitHub), read_commit and read_tree (None when the version does not exist), list_commits (versions reachable from main and the kept forks, newest first), write (writes a commit without a ref, keeping the parent's files outside the five folders; None when the same commit already exists), keep (a fork ref), fetch (the shared main: GitHub's after a fetch, or the mirror's own main in local mode; None when there is none), is_ancestor, merge_tree(base, ours, theirs) (a three-way merge of the five-folder trees; MergeConflict with the paths on conflict), push (a non-force push to GitHub's main, or a fast-forward of the local mirror's main; False when refused), and initial_tree (the first local main's tree, or None). GitVersionStore(directory, url="", *, ssh_key="", hooks=None, seed=None) runs the git CLI with asyncio.create_subprocess_exec (GIT_TERMINAL_PROMPT=0, LC_ALL=C, and GIT_SSH_COMMAND with the deploy key when ssh_key is set; cancellation kills the child). The constructor picks the strategy: with a url, _GitHubUpstream sets remote.origin.url and implements fetch and push over the network; without one, _LocalUpstream returns the mirror's main from fetch, moves it only by fast-forward in push (is_ancestor then move_main), and reads the seed package's five folders with snapshot.package_tree off the event loop for initial_tree. The repository is created as a bare repository on first use only in GitHub mode or in local mode with a seed; otherwise it only reads an existing repository (the check CLI). hooks is set as core.hooksPath every time it opens. The module function ensure_working_copy(mirror, path) runs git clone --branch main <mirror> <path> when path does not exist. Refs of the mirror: MAIN_REF (refs/heads/main, the adopted main the runtime runs), REMOTE_MAIN_REF (refs/remotes/origin/main, GitHub's main at the last fetch), and FORK_PREFIX (refs/te/forks/<id>, optimizer candidates, never pushed). A version's tree is the regular files (modes 100644 and 100755) for which snapshot.owned is true; symlinks and submodules are left out, and file modes are not kept. read_commit and list_commits parse one git log format (_parse_commits); move_main runs git update-ref with the old value; write keeps the parent's entries outside the five folders (_inherited_entries), writes the blobs (_blob_entries), builds the tree in a temporary index (_write_tree), and writes a commit object with a fixed author; fetch updates REMOTE_MAIN_REF with +refs/heads/main; merge_tree runs git merge-tree --write-tree with an explicit merge base; a successful push also moves REMOTE_MAIN_REF. Only GitHub's fetch and push use the network, and error messages mask credentials in URLs.

Usageopen_repo constructs it with config.COMPONENT_REPO_DIR, COMPONENT_REPO_URL, COMPONENT_REPO_SSH_KEY, HOOKS_DIR, and PACKAGE_ROOT for the runtime; the check CLI constructs a read-only one over --repo. Repo's start, refresh, sync, fork, merge, log, and tree read and write through it; build_runtime calls ensure_working_copy in local mode.

Rules it follows

  • A version id is the commit SHA; the same tree, parent, message, and second always give the same commit, so write reports an existing commit instead of creating a duplicate.
  • move_main is a compare-and-swap through git update-ref <ref> <new> <old>: when several processes move main at the same time, only one succeeds; it never changes GitHub.
  • Writing a version replaces only the five folders; the parent's other files (such as README.md) are kept, so a pushed version keeps the repository's docs.
  • Only the GitHub strategy's fetch and push use the network, and push never forces; in local mode push only fast-forwards. Construction does no I/O; the mirror is created on first use.
Pitfalls
  • Objects of a write whose load fails stay unreferenced in the mirror until git's garbage collection; only main and the kept forks protect versions.
  • File modes and symlinks are not part of a version: write stores every file of the five folders as 100644, so executable bits are lost when the optimizer rewrites a tree.
  • Requires git 2.40 or later (merge-tree --write-tree with --merge-base).
  • list_commits reads the whole history reachable from main and the forks without pagination.
