Dependencies between core and components

Placement and connections of the composition roots, shared infrastructure and version-owned components · based on the code in the working tree

Documentation guide · core · components · Component versioning · FastAPI management features

Agents run from the main of the version store (Repo) through the run handle. Components live in the component repository, and the Host never imports or calls them. core/abc uses the pure builtin/domain and does not depend on the ORM. builtin/app.py connects the outer implementations. core/builtin/app.py passes shared services as HostServices (open_host_services()), and the version-owned agent/compose.py builds the component graph. Dependencies from version-owned components on core services and contracts and on Host modules are allowed (a child request goes through publish_child in queue/child.py). From the Host side, version components are reached only through dynamic loading into per-version namespaces, the run handle (RunVersions: the Runtime's dispatch entrance and call_agent's child lookup), and the main component graph (catalog). Versions are commits of the component repository read from its bare mirror; periodic component work runs as agents started from the schedule table.

Every execution request, whether from an external event, the CLI, a scheduled trigger or a child request of a component (automated development, the next Sentry item, the PR retirement sweep), is saved in Redis as an EventRequest, and the Runtime hands it to the version's dispatch agent (agent/dispatch.py). 3. Evidence for the connections

ConnectionCodeResponsibility
Composition root → Host, version storecore/builtin/app.pyAssembles the named LLMs (max, high, low, flash, flash_low), logs and Stores with open_host_services() and passes them to versions as HostServices. Starts the version store and loads the mirror's main (when the mirror has no main, it fetches GitHub's main and adopts it once it loads; a failure aborts startup) before creating the Runtime, which syncs with GitHub's main every COMPONENT_FETCH_INTERVAL
Composition root → child requestscore/builtin/app.py / queue/child.pyprepare_runtime_state installs the runtime's Producer with child.install; components publish requests with the running message as parent through publish_child (external_id <message id>:<key>). The maintenance tick only saves the catalog and the heartbeat
Version → component graphagent/compose.py / builtin/compose.pybuild_agents creates one instance per agent class with the client named by llm and checks that the child names each class declares in agents are in the list (child instances are not bound; unknown or duplicate names fail the version's assembly). It bundles the entrances, SOURCES, fetch_source, the mesh and skills, and returns a ComponentGraph (all agents, entrances, sources)
Runtime → version storeversioning/repo.pyAt each run start, refresh() reads the mirror's main and, if it differs, loads it outside the event loop and switches. The run handle RunVersions returns, per name, the main first obtained until the run ends, and release at the end releases versions that are neither main nor in use
Version store → component repositoryversioning/store.pyGitVersionStore runs git against the bare mirror COMPONENT_REPO_DIR (refs/heads/main = adopted main, refs/remotes/origin/main = GitHub's main at the last fetch, refs/te/forks/<id> = optimizer candidates). Moving main is a compare-and-swap (move_main); only fetch and the optimizer merge's non-force push use the network, and the mirror's main moves only after a push succeeds
Check CLI → version storeversioning/__main__.py / scripts/component-hooks/python -m trackeverything.core.versioning check [--repo <git working tree>] [<rev>] loads a commit with the same open_host_services() and prepare_components as the runtime and prints ok <SHA> or the failing path and line. The pre-push hook of a component clone and the pre-receive hook of the local mirror run it for every new main. It neither reads nor writes the runtime's main
Redis → execution and ACKconsumer.py / runtime.pyThe Runtime caps running tasks at RUN_CONCURRENCY and receives messages one at a time from QueueConsumer; in a task with a copied context it checks the mirror's main and obtains dispatch through the run handle. It builds the AgentContext from the EventRequest, decides the run_id and session, and performs start record → dispatch agent → result record. Runs in the same session also run in parallel. RUN_TIMEOUT cancels the run. The Runtime does not ACK; the dispatch agent runs XACK and XDEL through ctx.ack. Unacked messages are reclaimed after 30 minutes and move to dead after more than 3 deliveries
HTTP → publish functionintegration/webhookCreates POST /webhook/{name} per Connector, durably enqueues the format-validated raw EventRequest and returns 202. core does not import api/
External connections → Producerconnector.py / integration/webhook/github.pyThe queue connects the intake SDKs and validation functions. The runtime's Runtime does not route by provider and hands everything to the dispatch entrance
Slack → enqueueintegration/slack.pyDurably enqueues deliveries for the target team and channel as raw events, then sends the SDK ACK. dispatch delegates to slack, which summarizes mentions of the owner and notifies Discord
Scheduled trigger → enqueueintegration/schedule.pyReads the schedule and reservation tables (through the core/orm connection) at most every 30 seconds and durably enqueues named runs at cron times and reservation times. It never writes the tables
Cross-version stateshared_state.pyshared(), keyed_lock(), task_lock(). A lock wraps only one operation inside a tool. TaskLock is not reentrant; a task that holds a lock and requests it again gets RuntimeError
Management API → catalog, run recordsapi/catalog.py / api/runs.pycatalog returns the snapshot of the main component graph that the runtime saved to Redis (code_version is main's c.<first 8 characters of the version id>) and the liveness state. The run flow and run statistics read logs and session_run
