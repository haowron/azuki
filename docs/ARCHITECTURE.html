The queue accepts, the runtime executes,
agents decide what to do.

The queue process accepts external input and writes it to Redis Streams. The core of the runtime process takes messages one at a time (up to 20 in parallel by default), loads the latest main of the components, and runs the single entry agent, dispatch. The queue carries only one kind of request, EventRequest; the dispatch agent interprets it, delegates and ACKs, and business decisions belong to agents, skills and tools. Read through the diagrams and expand only the contracts you need.

This page owns the Host's shared contracts. Application-flow examples require separately installed components; the package defaults contain only dispatch, general, and optimizer. See component ownership for the boundary and the location of workflow specifications.

Current implementation · 2026-10-13

Wide diagrams scroll horizontally.

The two processes never call each other directly; they hand over messages and state through Redis and PostgreSQL. Review reports are additionally handed over through the shared directory REPORTS_DIR (written by publish_review_report in the runtime, read by /reports/* in the queue). The queue process is started by scripts/start_queue.sh (python -m trackeverything.api) and serves webhooks, the management API and pages on a single HTTP server. The runtime process is started by scripts/start_runtime.sh (python -m trackeverything.core.builtin) and writes the component catalog to Redis for the management API to read. The CLI (python -m trackeverything.queue.cli publish) and derived requests inside the runtime also write through the Producer class; each process creates its own instance with Producer.from_env(). The core box is drawn inside the runtime process because Runtime runs only there; the queue process also uses core's request contract (core/abc/submission.py) and database access.

The queue stores before it responds; the runtime takes and executes

TrackEverything runs as two independently started processes, and the durable boundary between them is Redis Streams. The queue process (python -m trackeverything.api, started by scripts/start_queue.sh) accepts GitHub and Slack webhooks and the always-on Discord and Slack connections. It only validates the format and prunes by sender identity (Discord) or by team and channel (Slack Socket Mode), writes the raw EventRequest to Redis with XADD, and only then responds to the sender. It runs no agents and no LLM. The runtime process (python -m trackeverything.core.builtin, started by scripts/start_runtime.sh) takes messages from Redis one at a time, loads the latest main of the components, builds an AgentContext and runs the single entry agent, dispatch, which acknowledges with XACK and XDEL. The diagram below follows a GitHub PR webhook from receipt to ACK.

queue processaccept and store

  1. Receive and check The request reaches POST /webhook/github on the queue process (upstream 127.0.0.1:18080) through the public path (Cloudflare Tunnel → nginx → auth service). When WEBHOOK_TOKEN is set, a mismatched X-Webhook-Token returns 401; a body that is not a JSON object returns 422. The shared intake in integration/webhook runs these checks uniformly, and no provider can bypass them.
  2. Wrap raw parse_github requires only the two headers X-GitHub-Event and X-GitHub-Delivery (422 when missing) and does not judge by event type, action or content; ping and successful workflow_run events are published too. It builds EventRequest(provider="github"): external_id is X-GitHub-Delivery and payload is {"headers": …, "body": <raw body>}. The headers keep only x-github-event, x-github-delivery and x-github-hook-id; authentication headers never reach Redis. This stage has no I/O and attaches no session.
  3. Persist Producer.publish serializes the request to JSON and runs XADD te:{<namespace>}:queue * data <JSON> (<namespace> is QUEUE_NAMESPACE, default trackeverything). The returned stream id is the message's only ID (message_id). Publishing does no deduplication: a resend of the same delivery becomes another message.
  4. Respond After confirming that XADD succeeded, it returns 202 and {"ok": true, "run": "queued", "message_id", "accepted_at"}; accepted_at is the time (in seconds) encoded in the stream id. When the Redis write fails, it raises QueueUnavailableError and returns 503 without a message_id.

runtime processread and execute

  1. Read The Runtime read loop first acquires a concurrency slot (RUN_CONCURRENCY, default 20, overridable by the environment variable of the same name) and only then reads; when no slot is free it does not read, and messages wait in Redis. QueueConsumer.next() first uses XAUTOCLAIM (min-idle 1800 seconds, COUNT 1) to reclaim one pending entry not ACKed for more than 1800 seconds and reads its delivery count with XPENDING; only when nothing can be reclaimed does it read one new message with XREADGROUP (group and consumer both runtime, COUNT 1, BLOCK 1000 ms). A message whose delivery count exceeds 3, or whose data cannot be parsed as an EventRequest (including the legacy forms agent.run and source.run), is not executed and moves straight to the dead stream.
  2. Prepare Each message runs as one task in a copied context. repo.refresh() first checks the main adopted in the component repository's mirror and, when it differs from the loaded one, loads it and switches; then repo.run() creates the run handle for this run. The entrance dispatch and each child agent obtained later pin their version when first obtained, until the run ends. The Runtime neither interprets the request nor routes by provider: every EventRequest becomes the entrance dispatch (config.DISPATCH_AGENT), data={"event": {provider, external_id, payload}}, request=None, and the session and parent session given by the publisher. The Runtime issues a new run_id, creates a session when there is none, builds an AgentContext carrying message_id, acknowledger, the run handle (agents) and MAX_STEPS (300), and writes the start of the session_run to PostgreSQL with begin_run.
  3. Run agent The dispatch agent runs within RUN_TIMEOUT (default 3600 seconds). It passes raw GitHub events to github, which, under Python control, delegates PRs to pr_event, CI failures to ci_failure, issue assignments to the owner to issue_investigation, and issue closes to issue_cleanup. Valid events out of scope are ignored with a reason, and invalid required fields are errors. Deliveries that already succeeded are skipped. It sets the Source definition and identity in ctx.data, and the child's fixed tool fetch_source fetches the current content. Children share the same Context and LLM step budget, and events for the same PR also run in parallel. When the run ends, finish_run records the result.
  4. ACK dispatch calls ctx.ack(ctx.message_id) when processing ends, which sends XACK and XDEL; an ACKed message does not remain in the stream. Events that run no child agent and error results are ACKed as well and are not retried automatically. When dispatch's processing raises before the ACK or is cancelled by RUN_TIMEOUT, the message stays pending and is reclaimed 1800 seconds after its last delivery. The Runtime itself never ACKs.

Independent startup and shutdown

The two processes start and stop independently and never launch each other. At startup both require the PostgreSQL schema to be at alembic head. The queue process first sends PING to Redis and then opens HTTP and the always-on connections. The runtime process closes running records left over from the previous run as interrupted, loads the main adopted in the component repository's mirror (when the mirror has no main yet, it fetches GitHub's main and adopts it once it loads; a failure aborts startup), creates the consumer group (MKSTREAM, id 0, kept if it already exists) and starts reading. The queue alone can still accept and store, and the runtime alone can still consume the messages left in the stream as well as new publishes from the SDK and CLI. /healthz reports that HTTP is alive and /readyz whether the Redis PING succeeds; a stopped runtime does not make it unready. At startup and on every maintenance tick (30 seconds), the runtime writes the component catalog and a heartbeat to Redis at te:{<namespace>}:catalog; the queue's /api/catalog reads it and treats the runtime as online when the heartbeat is less than 60 seconds old.

The Runtime class does not know about Redis. It depends only on the MessageQueue protocol (prepare, next, ack), and ack is only handed to the Context as acknowledger for the dispatch agent to call. QueueConsumer in queue/consumer.py implements the protocol and handles the 1800-second reclaim, the limit of 3 deliveries and the dead stream; each message reads the latest main adopted in the mirror when its execution starts.

Guarantees and limits

  • Acceptance responses (HTTP 202, the Slack Socket Mode ACK, the success followup for Discord buttons) are returned only after XADD succeeds. When Redis is unavailable, HTTP returns 503 and reports no acceptance.
  • Publishing does no deduplication, and external_id is not used for deduplication either. External resends (such as GitHub redeliveries) and duplicate publishes by a maintenance sweep each run once as separate messages.
  • Delivery is at-least-once, and each message runs at most 3 times. A message still not ACKed after running for more than 1800 seconds can be reclaimed while it runs and executed twice. External posts, Git operations and the ACK are not in one transaction, so external side effects are not guaranteed to happen exactly once.
  • FIFO across the whole queue is not guaranteed. At most RUN_CONCURRENCY tasks run at once, and that is the only concurrency limit; runs for the same session, PR or issue also run in parallel. Neither the Runtime nor agents serialize by business object, and the resulting duplicates, reordering and conflicts are accepted (locks and shared state).
  • When one process stops, the other keeps running: while the runtime is stopped, the queue still accepts and stores; while the queue is stopped, the runtime still processes the messages in Redis. Webhooks that arrive while the queue is stopped depend on the sender resending them, and missed Discord messages are not caught up; a failed publish of a Discord message is only logged.
  • A message that was executing when the runtime was forcibly terminated is reclaimed and re-executed only 1800 seconds after its last delivery.
  • Redis should run with --appendonly yes --appendfsync always --maxmemory-policy noeviction (the default in docker-compose.yml); the application does not check these settings. Without them, accepted messages can be lost.
  • Each Redis operation sends its commands in sequence, and consistency is not guaranteed when one fails midway; for example, the same message can enter the dead stream twice.
  • Only one queue and one runtime are started per DB and namespace. This is an operational convention; no lock prevents duplicate starts.

The Runtime does not depend on FastAPI or the intake SDKs and does not reference Sources; it only hands the EventRequest from the queue to the dispatch agent. HTTP, intake, the CLI and requests inside the runtime all write to Redis Streams through the shared asynchronous Producer.publish, and the Runtime reads them one at a time through QueueConsumer. The intake side does not import execution-side types such as Runtime and Repo. The Source definition is built without I/O by github for GitHub events and by dispatch for named runs. The agent core (BaseAgent's control) does not reference Sources; fetching is the job of the concrete tool fetch_source (tools/source_fetch.py).

Replacement happens at assembly time through Python declarations, registration and function injection. Base classes and interfaces are imported from trackeverything.core.abc, and pure log and error values and in-run state from their defining module, trackeverything.core.builtin.domain. There is no automatic plugin discovery or installation. A push to the component repository's main is used from the next run once the runtime's sync fetches it, loads it and adopts it as main (within COMPONENT_FETCH_INTERVAL, without a deployment), without interrupting work in progress. Each agent name in a run uses the version obtained first until the run ends (component versioning). For Host-side changes, the supervisor decides per process (restart_roles), restarts only the affected process, and waits for accepted work to finish before restarting.

The Runtime builds a Context from the request and wraps execution in records

In the runtime process (python -m trackeverything.core.builtin), the Runtime executes one run for each valid message it reads (a redelivery is a new run). The Runtime reads through the MessageQueue protocol (prepare / next / ack), which QueueConsumer implements with Redis Streams.

EventRequest is the JSON stored in the queue (strict, immutable fields; unknown top-level fields are rejected) and holds no run_id, functions, agent instances or authorization (authorization and run_id cannot be put in a request). kind is only event.handle; messages in the legacy forms agent.run / source.run cannot be read and move to the dead stream. The Runtime (core/builtin/runtime.py) reads one message when fewer than RUN_CONCURRENCY (default 20) tasks are running. In a new task that copies the current context, it first reads the latest main adopted in the mirror with repo.refresh(), then creates the run handle (RunVersions) with repo.run(), and converts each request into the entrance DISPATCH_AGENT (dispatch), data = {"event": {provider, external_id, payload}}, request = None, and the session and parent session from the request. The Runtime does not route by provider or payload and does not reference Sources.

A named run (Queue) reaches only the child agents that dispatch declares in agents: github, general, project_qa, issue and slack, used on event routes, and pr_event, ci_failure, issue_investigation, issue_cleanup, project_memory, review, document, pr_cleanup, sentry_autofix, sentry_autofix_item, optimizer, reservation_fire and maintenance, which can also be run by name. For an undeclared name, both data and source, data that is not an object, source that is not a string, or source_kwargs that is not an object, no child agent runs and the run ends with an error. The data form replaces ctx.data with data, and ctx.data is empty when neither is given; the child's request is the payload's request, and authorization is not set. In the source form, dispatch takes the Source class by name from its own version's Source dictionary and writes source / source_kwargs / project into data without I/O, writing the identity seed only when the pure computation Source.identity_for can derive it. For an unregistered source or a failed derivation, it only passes the definition and runs the child agent as usual, and the in-run fetch_source records the fetch failure. Fetching the snapshot is deferred into agent execution: at the start of the entry agent's _execute, Python control calls the fetch_source tool exactly once, writing identity / payload / project / source_description into the data of the same Context (once per run; repeated calls on the same Context are memoized). The fetch target cannot be specified through the LLM's JSON arguments.

The Runtime issues the run_id (uuid4().hex) before execution and creates a session (uuid4().hex) when the request has none. It builds a new AgentContext from a deep copy of data, MAX_STEPS (300), message_id, the reading side's ack (acknowledger) and the run's handle (agents), pins the entrance version with run.version("dispatch"), and takes dispatch from that version's component graph when the name is in its entrances (ENTRANCES in agent/compose.py contains only dispatch). The start and end of the session_run are recorded with the entrance's version. During execution, REQUEST_ID holds the message_id. When the run ends (success, failure, cancellation, deadline), repo.release(run) returns the handle. authorization is None in the root execution; only the dispatch agent sets it, after re-verification and before calling a child agent (Discord confirmation buttons and automated development). It is never put in data, LLM arguments, log snapshots or session JSON.

When the entrance version's entrances lacks dispatch, the result is an entrance error (unknown entrance: dispatch); exceeding RUN_TIMEOUT (default 3600 seconds) cancels the whole agent tree, and the result is cancelled with a deadline note; an unexpected exception raised by agent.run is an execution error. These results belong only to that run and do not affect other messages; entrance, execution and session errors also write the cause into response. BaseAgent.run() is the agent's try/except boundary: except for cancellation it does not re-raise, and instead converts exceptions into an error result with structured errors. Every result other than ok carries an ErrorNote (budget for max_steps). Callers decide whether to continue from status and read details from errors (they do not parse the response string). ErrorNote.cause keeps the original text verbatim, untranslated.

A parent agent runs a child agent only through call_agent(call, name, request): LLM calls and Python control take the same path. The child instance is obtained by name from call.ctx.agents, and call.child(request) references the same Context object; when the name is not a child or no instance can be obtained, nothing runs and a delegation error is returned. The version's agent/compose.py calls build_agents (core/builtin/compose.py) to build one instance per name, checking only that the child names each agent declares in agents exist, without binding child instances. Within one run, a name always uses the instance of the version obtained first. Data changes and the step budget are shared across the whole tree; request / response belong to each call. Child calls neither copy nor serialize data, and a child's result does not overwrite the parent's output. The result of a child agent called by the LLM returns to the parent as the observation {name, ok, status, output, error}, where error lists the ErrorNotes' original text (stage: cause). Agents do not know how they were started and always satisfy the coroutine run(call: AgentCall) -> AgentResult.

Every run has a session; one session links many runs, and the parent and child agents / harnesses / tools of one run share the Context's IDs. The Runtime does not serialize by session: runs in the same session also run in parallel, and the queue as a whole does not guarantee FIFO, so conversation history can be recorded in a different order from publishing, and parallel runs do not see each other's messages. Each run executes once, in order: record the start (begin_run creates or reuses the session in one transaction and writes the entrance name, data, request and code_version) → run the dispatch agent → record the result on the same run (finish_run). Named runs are also recorded as agent_name="dispatch", request=None, so a named run that specifies a session reads past requests as None when it reads conversation history. A run whose start record fails runs no agent and returns a session error. A failure to record the result does not change the result; the row stays running and becomes interrupted during recovery at the next runtime process startup. When the caller cancels the task, the run is recorded as cancelled and the cancellation keeps propagating.

The Runtime does not ACK. The dispatch agent calls ctx.ack(ctx.message_id) when processing ends (including events it does not run, named runs and delegations that end in error). Runs cancelled by the caller and messages for which dispatch never reached the ACK (failed start record, no dispatch in the entrance version, deadline cancellation, an exception in dispatch itself) are not ACKed: the message stays pending, QueueConsumer reclaims it after 1800 seconds, and it moves to the dead stream after more than 3 deliveries (§8). So a named run cancelled by RUN_TIMEOUT is also re-executed through reclaim (up to 3 deliveries).

Conversation input is published by the queue process intake (integration/discord.py) as a raw EventRequest with session_id / parent_session_id. Discord resolves one session per channel through the channel mapping table (resolve_session of channel_store); a thread uses its parent channel's session as the parent session, and the general channel gets no session. Conversation entrances (general, project_qa) are forced by Python control to read conversation_turns (successful exchanges in the session and its ancestor sessions) during execution. The dispatch agent delegates raw Slack events to slack. For a direct mention of the owner, it reads the thread and the recent conversation and sends a concise summary to the existing Discord notification destination. The general channel's history is fetched from the API of the one configured Discord channel. It passes the union of the exchanges within the last two hours and the latest five turns, oldest first, and does not search all channels by session. Issues / PRs and projects use the successful exchanges of the current and ancestor sessions and restore the body from the raw event. Every route keeps a character limit. See Agent inventory and Session.

Contract §3 · Agent loop and harnesses

BaseAgent is a concrete class. The public entry point run() is final and is responsible, in order, for the delegation depth check, pre harnesses, _execute(), post harnesses on success, arbitration of unresolved tool failures, and run logs. Python control is changed by overriding _execute(). The standard _execute() (_execute_llm_loop()) repeats the following.

  1. Builds the prompt from the call / Context (system is get_prompt(), user is the JSON of request and data) and passes tools and child agents to the LLM as a flat list of callables.
  2. On FinalAnswer it ends; on Calls it selects tools / child agents by name and executes them (child agents through call_agent).
  3. Adds the observations to the history and continues within the shared step budget; when the budget runs out, it ends with max_steps.

Every LLM call an agent makes, in the standard loop or with messages it builds itself, goes through _respond_one_step(), which sends a copy of the messages headed by the version's agent/SYSTEM.md: prepended to the first message with a blank line when that is a system message, otherwise as a new first system message. The caller's messages are unchanged, so it never repeats across steps. Harnesses and the optimizer call their LLM client directly and receive nothing. prepare_components binds the file to every agent of the version; a missing or blank file adds nothing, and one that is not UTF-8 or longer than 8,000 characters fails the version's composition. People maintain it; the optimizer never writes it (Component versioning).

Child agent calls listed side by side in the same response run in parallel as one group (asyncio.TaskGroup). A tool call is a barrier: after the preceding group completes, tools run one by one in call order ([A, B, Tool T, C] is {A, B} → T → C). A group with only one child agent runs in the caller's task, and observations are added to the history in call order, not completion order. A child agent's run() converts exceptions into results, so a failed child does not cancel its siblings. A name that was not offered to the LLM is not executed and returns callable was not offered as the observation. An agent whose callables include child agents adds the call-order rule (PARALLEL_CALL_RULE) once, in the first system message, so that calls that use other results are deferred to the next response. A Python-controlled parent awaits a child whose result it uses before calling the next one, and calls only independent children in parallel through agent/fanout.py's settled (waits for all to finish, then raises the first exception with its original type; results come back in argument order): issue_investigation investigates four media with research, then calls web_research, investigator and document (for the issue report) in order. project_memory waits for compare's result and calls the project sync only when something changed. dispatch runs the acceptance reaction of every accepted Discord message in parallel with the entrance it delegates to (general, project_qa or issue) and waits for it to finish before the ACK. Parallel children do not read and write the same data / tool_state key across an await.

The Runtime sets config.MAX_STEPS (300) on the Context. Before each LLM call, advance_step() consumes budget, and parents, children and parallel siblings use the same counter in arrival order (on a single event loop there is no await between the check and the increment, so the limit is never exceeded). Agent constructors do not set a budget of their own. Python processing that does not use the LLM consumes no steps.

The Runtime wraps the entrance run in a deadline of config.RUN_TIMEOUT seconds (environment variable RUN_TIMEOUT, default 3600). A timeout cancels the whole agent tree; on cancellation, stop_process_group in tools/command/process.py reaps the whole process group of any subprocess started by a tool. The Runtime returns a cancelled result (ErrorNote(stage="deadline", cause="run exceeded <n>s")).

Added children, like declared ones, are obtained by name from the run handle at execution time. It is disabled by default, and each agent keeps its declared composition. Child-agent delegation depth is capped by MAX_AGENT_DEPTH (16, core/abc/agent.py): cycles formed by declarations among shared instances and cyclic delegation in the mesh are contained by the shared step budget and this cap, and the boundary converts a run that exceeds the depth into a structured error result.

Even tools exposed to the mesh go through the runtime permission checks. The parent execution ID at the call boundary is kept in a Python ContextVar and is never received from the LLM's JSON.

PreHarness / PostHarness are ABCs. They are not included in the LLM's prompt or callables; run() evaluates them unconditionally. Checks and reactions are coroutines. Each check records one harness event as a child of the agent. An exception in the body is converted by the run() boundary into a structured error result, and post does not run. By convention, harnesses treat the Context as read-only, dispatch no agents, and hold no mutable state across executions. The fatal notes are attached once, at the run boundary below. The loop contract of other agents is unchanged.

Error boundary and ErrorHarness

run() wraps depth check → pre → body → post (when ok) in one try/except and handles failures in the following order.

  1. An exception (including exceeding the delegation depth) is converted into an error result whose errors are ErrorNote(stage="execution", cause="<type>: <message>") plus all unresolved tool failures of this execution.
  2. When a non-ok result still has no errors after the fatal failures of the next item are appended, the boundary adds a note: ErrorNote("budget", "used all <n> LLM steps") for max_steps, and the agent name as stage otherwise.
  3. Of the unresolved tool failures (see §4), only those declared in fatal_tools turn ok into error or are appended to the errors of a non-ok result; the remaining unresolved failures of an ok result are only logged. Unresolved failures are consumed at each boundary and do not leak to the parent's boundary.
  4. After the result is saved as one agent log event (with the note list in error), and only when the status is error, the ErrorHarness.handle(call, result) handlers of on_error are called in declaration order.

Cancellation (the run deadline or cancellation by the caller) is not converted into a failure. Each interrupted agent and tool leaves one cancelled log event, and the cancellation propagates upward without calling ErrorHarness.

ErrorHarness is a third protocol, for reactions only: it treats the result as read-only and only performs deliveries such as notifications. Its own exceptions are suppressed and logged by the boundary and never mask the original failure. max_steps / cancelled do not take the error path. The existing implementations are FailureNotify (pr_event) and IssueFailureNotify (issue_investigation) in harnesses/failure_notify.py: they deliver failure notifications through NotifyTool, keeping stage: cause verbatim and translating only the explanatory frame with one direct LLM call; they call advance_step() before translating and fall back to the English frame when the budget is insufficient or translation fails, without blocking delivery.

Contract §7 · Persistence boundaries

Concrete tools own the persistence of the input and material an agent operates on, and AgentContext owns the shared state during execution. The Runtime owns sessions and their run records as the record of execution control, stored in session / session_run of PostgresSessionStore. The Runtime issues a run ID per message and does not serialize by session. It first uses begin_run to create or reuse the session and insert the run with status running in one transaction, then runs the dispatch agent, and afterwards writes the status, response and end time with finish_run. When recording the start fails, no agent runs; a failure to record the end does not change the result: the row stays running, and at the next runtime process startup, before the queue is read, recover_interrupted_runs closes it as interrupted. The statuses written are running, ok, error, max_steps, cancelled and interrupted. The session's string primary key and the run's foreign key guarantee the one-to-many relationship, and parent_session_id references the parent session in the same table and is set only when a session is created. See Session infrastructure for details.

PostgresChannelStore owns the channel mappings. The channel table assigns one session per provider × channel_id, and concurrent creation converges to one row through the primary key and ON CONFLICT. The queue process's Discord intake resolves the session before publishing a message: the general channel gets no session, and a thread uses its own session, with the session of its parent channel (other than general) as parent_session_id. session_source stores the original URLs of materials linked to a session, and project_channel stores the mapping from a project to its announcement channel (channel_id is unique). channel and session_source have no foreign key to session, because a channel mapping can be created before that session's first run. The Python control of pr_event, pr_cleanup and Project reads and writes these mappings through the channel_link tool.

A Codex CLI conversation has a separate UUID, and ImplementationAgent links it to the app session in the codex_session table through the codex_session tool. Links are independent per session / checkout / project / mode, and a different ID already saved is never overwritten; completed conversations of the current and ancestor sessions are passed to the implementation and to the independent reviewer. Resumption, history and saving the actual ID are owned by ImplementationAgent. For issues, spec / grill / harness save the per-stage CLI UUIDs and the development state in memory. A conversation separate from general is created through the shared session resolution, and a dedicated clone is kept outside the workspace pool (REPOS_DIR/issues). The contract for spec, cases, confirmation, publishing and channel cleanup is owned by Issue development. A PR close keeps the shared issue channel; on an issue close, issue_cleanup confirms that the issue is still closed and deletes the dedicated channel. The issue_channel tool clears the development record's channel ID and source link and keeps the session history, spec and cases.

record_event starts no agent; in one transaction it creates or reuses a session and appends one completed run with status ok (the Store issues the run ID). After an issue-assignment investigation delivers its report, the record operation of the issue_channel tool records that report as a response in the issue channel's session; the receipt record issue-investigation:<identity> in memory keeps the same assignment from being investigated twice. This Store requires PostgreSQL.

Compare's baseline keeps the existing Source identity key and is not mixed with the conversation-note key note:<identity>. A baseline that is invalid JSON or not an object is recovered with the recover_baseline tool. The basis is the input payload of successful Compare logs for the same identity, limited to the newest object among the records that ended before the corrupted row's saved_at. Records of other identities, failures, future records and invalid records are not used. It rechecks the current state under a row lock, saves the corrupted value and the original saved_at as is under a baseline-backup: key, and replaces the value in the same transaction. If the value is already valid, nothing changes. Without a basis, or on a DB failure, it keeps the original value and returns unfinished. Recovery does not include reinitialization as a first run, notifications or webhook resends. After recovery, the regular comparison continues, and the success or failure of saving and notification is judged as usual.

Sources do not store baselines. PostgreSQL owns the business state: the one database that DATABASE_URL points to; an environment without it fails at startup (there is no fallback). workspace pool (always-on clone rack)

The working checkouts for review, fix and investigator come from the always-on clone rack managed by workspace_pool (tools/workspace_pool.py). Slots live under REPOS_DIR/pool/<owner__repo>/slot-<n>/ and consist of the always-on clone repository/ and per-execution workspaces. Each repo starts with POOL_INITIAL_SLOTS (3) slots and grows without limit when no idle slot is available; a new slot is copied locally from an existing slot's clone (git clone --local, sharing objects through hard links, without network access) and is cloned from GitHub only when copying fails. Rows and directories are never deleted. A PR binding (pr_number not NULL) lasts until the PR closes, and the same PR reuses the same slot first (from the second time on, it only fetches instead of cloning). A repo binding (NULL) is for investigator; it returns to idle after each execution and can be rebound by a PR. busy is execution-level mutual exclusion applied per PR head (per-head admission): an acquisition passes the head, and while the slot for the same PR and head is busy, new acquisitions for that head are rejected (HeadBusyError names the holder; review, full review, arbitration and fix are not distinguished). When the process that held that busy slot is confirmed to have ended (for example a run interrupted by a restart; never fix-pending), the acquisition reclaims the slot on the spot instead of being rejected. Acquisitions for a different head, without a head, or for other PRs are accepted in parallel. While waiting for confirmation, fix keeps the slot busy with holder fix-pending, and other executions for the same head are rejected meanwhile. This is how a review mode runs only once per head (see PR review). The workspace_slot table (PostgreSQL, through the ORM) is the single source of truth for the state, and acquisition is decided in a single transaction (SELECT … FOR UPDATE). On every reuse, prepare_workspace cleans everything except repository/, verifies and repairs origin, fetches only the needed SHA (and the base branch when needed), and deterministically checks out and resets to the target SHA (git clean keeps .venv and env).

When a PR closes, pr_cleanup, delegated by pr_event, calls unbind: it unbinds idle slots, marks busy slots with unbind_requested, and unbinds them when the owner releases them. This step does not depend on the Discord settings or on whether a triage record exists. Daily maintenance is a component, not Host work: the schedule row maintenance (0 4 * * *, Asia/Tokyo, payload {"agent_name": "maintenance", "data": {}}) starts the Python-controlled agent maintenance (a child of dispatch, no LLM), which runs the tools workspace_sweep and pr_retire_sweep in that order; a failure of one does not skip the other, and any failure ends the run as error. workspace_sweep reclaims crash orphans that have exceeded the holder's deadline plus POOL_RUN_GRACE (300 seconds) and whose owner process no longer exists, checks whether the PRs of bound slots have closed and unbinds them (covering missed webhooks), and cleans up temporary review-* / fix-* directories under REPOS_DIR older than POOL_LEGACY_MAX_AGE (48 hours). pr_retire_sweep scans the PR triage records in memory that still have a channel_id, and for closed PRs publishes a named run of pr_cleanup with publish_child (the maintenance run's message as parent; covering executions lost for close deliveries).

Each acquisition holds a random lease_id, the owner owner_pid and the process start identity owner_process. release / hold verify the lease, so the end of an earlier acquisition never clears the busy state of a later reuser. reclaim re-verifies the lease, holder and time seen at scan time. Work with the same process start identity is never reclaimed, even past its deadline. PID reuse is treated as the original owner having ended. Only fix-pending may be reclaimed by TTL, and before pushing, the same lease is restored to fix. A stale pending entry is rejected before it touches Git. This judgment assumes the deployment contract of a single host and one PID namespace, and is not shared across hosts. On clone failure the lease is returned; Git uses the caller's overall deadline and is terminated together with its subprocess group. Investigator uses the in-process WorkspaceTool and releases its lease on completion, failure or budget exhaustion, so the subprocess environment of run_command (an allowlist) neither needs nor contains DATABASE_URL.

The lease_id, owner_pid, owner_process and unbind_requested columns are defined by Alembic revision d873c2a94e10. For safety, busy rows without an owner process identity (other than fix-pending) are not reclaimed automatically; check and handle them while the service is stopped. The acquire command of the operations CLI (python -m trackeverything.tools.workspace_pool) prints SLOT <id> <path> <lease-id>, and release requires <id> <lease-id>.

Contract §9 · Run logs

BaseAgent.run() records agents and harnesses at the shared boundary (each pre, post and on_error harness records one harness event), and TrackedLLM records llm events for the LLM. BaseAgent.call_tool() records each tool call as one tool event (only the arguments and success or failure, without the output; the output of LLM-initiated calls already appears in the conversation of the following llm event. Running work keeps its version; new work uses the new main

When A starts, the Runtime confirms with refresh() that the mirror's main is V1. A's run handle pins each name's version when it first obtains that agent by name (dispatch is pinned at the start), until A ends.

A version is a git commit and covers the regular files in the five version-owned folders agent / tools / skills / harnesses / sources at its root; other files (such as README.md) are not part of a version. People work in the working copy components/ of the checkout (COMPONENTS_DIR, ignored by this repository's git) and push to the shared main: the component repository on GitHub when COMPONENT_REPO_URL is set, otherwise (local mode) the mirror itself, whose first main is a commit Initial components of the package's default components and which the runtime clones into components/ when that is missing. The version id is the 40-character commit SHA, and records use the label c.<first 8 characters>. The version store Repo (core/versioning/repo.py) reads versions only from the bare mirror COMPONENT_REPO_DIR (default data/components.git; remote origin is COMPONENT_REPO_URL, fetched and pushed with the deploy key COMPONENT_REPO_SSH_KEY) through GitVersionStore (core/versioning/store.py): refs/heads/main is the adopted main, the only ref the runtime runs (in local mode also the main people push to); refs/remotes/origin/main is GitHub's main at the last fetch; refs/te/forks/<id> keeps the optimizer's candidates and is never pushed. Only GitHub's fetch and push use the network; reads in a run do not. Only a push to the shared main (a person's, or the optimizer's merge) changes main, and the mirror's main moves only by compare-and-swap from the value that was read. A process has exactly one version store: open_repo creates the singleton, which the runtime creates and optimizer uses through current_repo() (two version stores would share the module namespace of the same version, and a release in one would remove the other's modules). Changes to the Host files (core / llm / queue / integration / api, config.py and so on) and to pyproject.toml and uv.lock take effect when the supervisor restarts the process after accepted work finishes.

A person changes components in components/: pull, edit, commit and push to main. The Host's scripts/component-hooks check every new main with python -m trackeverything.core.versioning check --repo <repository> <sha> through the scripts/run_local.sh of the checkout that holds them: a clone of the GitHub repository enables its pre-push once with git config core.hooksPath <checkout>/scripts/component-hooks, and in local mode the runtime points the mirror's core.hooksPath there so that its pre-receive refuses a main that does not load or its deletion. The check loads the commit outside the event loop with the same open_host_services() and prepare_components as the runtime (modules load into the reserved namespace _te_versions.v_<version id>, and the component graph is built by that version's agent/compose.py), neither reads nor writes the mirror, and prints ok <SHA>; on failure it writes the path within the version, the line and the exception to stderr (exit code 1) and the hook stops the push. No deployment or import is needed: in local mode the next run's refresh() loads the pushed main; with GitHub, within COMPONENT_FETCH_INTERVAL (300 seconds) the runtime's periodic repo.sync() fetches GitHub's main, loads it and, only when it loads, adopts it as the mirror's main. A failed fetch is logged as a warning and a main that does not load is logged once at error level and not adopted (the hook can be bypassed, so sync validates again); in both cases the adopted main stays in use. On the first startup, when the mirror has no main, the runtime adopts GitHub's main once it loads, or in local mode the package's default components; a failure aborts startup.

At the start of each run, the Runtime reads the mirror's main with refresh() and, when it differs from the loaded one, loads it outside the event loop and switches; a load failure is logged once per version and a read failure is logged as a warning, and in both cases the already-loaded main stays in use. The run handle (RunVersions) records, for each name, the main at the time the name was first obtained and returns that version's instance until the run ends; a name not obtained yet uses the main current when it is obtained. A version that is neither main nor used by any run immediately releases its modules (aliases in sys.modules and attributes on the parent package), linecache, file view and component graph; the commit remains in the mirror. fork(parent, tree, message) writes a tree as a new commit whose parent is a stored version, loads and validates it, and keeps it as a fork ref without changing main; the same version can be forked many times. merge(version_id) reads the shared main R (fetching GitHub's): when the candidate is already contained in R, it pushes nothing and returns main; when R is the candidate's parent, it pushes the candidate as it is; otherwise it merges R and the candidate three ways (git merge-tree, with the candidate's parent as the base) into a new version whose parent is R and whose message ends with Rebased-From: <candidate id>, loads and validates it, and pushes it to GitHub (in local mode, fast-forwards the mirror's main by compare-and-swap). The push never forces, the mirror's main moves only after the push succeeds, and the result is the main Commit. A conflict raises MergeConflict, a rejected push or a main that moved PushRejected, network and git failures GitError, and a load failure its own exception; in every failure nothing is pushed and the mirror's main does not move. If main cannot be loaded at startup, startup is aborted: deploy a change of the contract between the Host and versions (such as the arguments of build_agents) in a form the current components still load with, and push the components afterwards; to recover, push a main that loads and point the mirror's main at it (deployment and restart).

The Host never imports or calls component modules. A component that queues a new request with the running message as parent uses publish_child in the Host's queue/child.py (the runtime installs its Producer there before it starts reading), and periodic component work runs as agents started from the schedule table (the daily maintenance agent runs workspace_sweep and pr_retire_sweep). Objects shared across versions and per-key locks are collected in core/shared_state.py (shared(), task_lock(), keyed_lock()), and every version's modules share the same copy. A shared value cannot be an instance of version-owned code, and releasing a version does not clear shared state. A lock wraps only one operation inside a tool; the Runtime and agents hold no locks. TaskLock is not reentrant: when the task holding it requests it again, it raises RuntimeError immediately instead of waiting; other tasks wait for the release.

Contract §8 · Host lifecycle and concurrent execution

The queue and the runtime are independent processes, each holding one asyncio event loop. The entry points are python -m trackeverything.api and python -m trackeverything.core.builtin; scripts/start_queue.sh and scripts/start_runtime.sh start them in the foreground through scripts/run_local.sh (which loads .env and resolves DATABASE_URL, QUEUE_REDIS_URL and QUEUE_NAMESPACE; WEBHOOK_PORT defaults to 18080). Both serve() functions first confirm with require_schema_head that the DB is at Alembic head and then hand over to process.run_host, which registers SIGTERM/SIGINT, runs start(), and runs stop() after a signal; stop() also runs when start() fails.

api/app.py assembles HTTP (webhooks, the management API and dashboard, /readyz) and the Discord/Slack intake. At startup it first pings Redis, then takes the HTTP port, then starts the always-on intake in registration order; /readyz reports ready only after all of them succeed. The shared Producer returns HTTP 202 and the Slack Socket Mode ACK only after XADD confirms the write; the Discord confirmation button defers first and notifies the owner of the result after the write. When the write cannot be confirmed, webhooks return 503 and Slack is not ACKed. Messages can be enqueued even while the runtime or the LLM is down.

core/builtin/app.py assembles the Runtime, QueueConsumer, the component version store (Repo), the session store, the maintenance tick and the component repository sync. The runtime's serve() prepares the process environment, resolves the code version, marks runs left unfinished last time as interrupted, builds the LLMs and stores and loads the mirror's main (when the mirror has no main, it fetches GitHub's main and adopts it once it loads; a failure aborts startup), installs its Producer in queue/child.py for the child requests of components, and saves the catalog, in that order, before it starts reading. It then starts the read loop, the maintenance tick (RECONCILE_INTERVAL, 30 seconds: the catalog and the heartbeat) and the periodic repo.sync() (COMPONENT_FETCH_INTERVAL, 300 seconds; a failed sync is logged and the next one runs on schedule). The Runtime reads one message only when fewer than RUN_CONCURRENCY tasks are running (default 20, overridable by the environment variable of the same name): it first reclaims with XAUTOCLAIM a pending entry idle for more than 1800 seconds, and otherwise reads a new message with XREADGROUP (blocking at most 1 second). Each message, in a task with a copied context, first reads the mirror's latest main with refresh(), obtains dispatch through the run handle, builds the AgentContext from the request, and directly runs the single entry agent, dispatch, within RUN_TIMEOUT (default 3600 seconds) (Queue). Runs for the same session, PR or issue also run in parallel, and concurrency is limited only by RUN_CONCURRENCY (locks and shared state).

The Runtime does not ACK; the dispatch agent ACKs through ctx.ack when processing ends, including events it does not run and named runs. The ACK deletes the message from the stream with XACK and XDEL. Cancelled tasks and runs that never reached the ACK are not ACKed, and the message stays pending. A pending entry not ACKed for more than 1800 seconds is taken again; this judgment looks only at idle time. Messages delivered more than 3 times or that cannot be parsed (including the legacy forms agent.run and source.run) move to the dead stream. There is no deduplication. A failure to record the session's end does not change the AgentResult; the row stays running and is marked interrupted at the next startup.

The Runtime issues the run_id; it is not part of the message. An explicit session is kept as is, and an unspecified session is created anew for each run. The fixed tool fetch_source fetches Sources within the run. The DB is awaited on the event loop through AsyncSession, and synchronous-only file processing goes to asyncio.to_thread.

Tool subprocesses use asyncio's process APIs directly, and the whole process group is reaped on completion, timeout and cancellation. Queue contract and operations covers reclaim, the dead stream and the SDK.

On shutdown, each process first closes new intake. The queue sets /readyz to not ready, stops the Slack and Discord intake and the HTTP server in reverse order (uvicorn waits for in-flight requests to finish), and finally closes the Producer. The runtime first stops the maintenance tick and the sync (waiting for one in progress), then lets the read loop end after the current read returns (messages read after the stop are not executed and stay pending), waits for every running task to finish, closes the version store (releasing every version), and finally closes the Redis connection. Neither process stops the other process or Redis.

scripts/run_service.sh queue|runtime is each process's supervisor. It is started by the LaunchAgent generated by scripts/render_services.py (RunAtLoad, KeepAlive) and logs to data/<queue|runtime>.log and data/<queue|runtime>.err.log. Every RUN_SERVICE_POLL (default 180 seconds) it computes a fingerprint of that process's Host files (membership is decided by process.restart_roles; components are not in this repository and reach the runtime through sync, without a restart). When the fingerprint changes, it sends TERM to the process group, waits at most RUN_SERVICE_TERM_WAIT (default 3600 seconds), then KILLs and restarts. When the process exits on its own, it restarts it after 5 seconds; when the supervisor receives TERM, it stops the process the same way and exits.

Contract §11 · HTTP and external adapters

Public HTTP comes in through Cloudflare Tunnel → nginx → a signature verification service, all outside the application. These independent processes are not part of the Host lifecycle, and the shared gateway can route to any local HTTP service. Public paths authenticate with any one of a GitHub signature, a Slack signature, Bearer, or a gateway session, and access restrictions on the public hostname and URL prefix belong to the Cloudflare side. Explicit public_read_patterns in the target route allow anonymous GET / HEAD only for the canonical paths of finished report HTML and pinned Mermaid assets; other resources, writes and the management API stay authenticated. The source of truth for ports, deployment and operations is CLOUDFLARE_TUNNEL.md.

The queue process's HTTP application is built by create_webhook_app(publish, extra_routers=..., connectors=...), where publish is Producer.publish. The application provides /healthz, the injected routers, and POST /webhook/{name} for each Connector that has a webhook; api/app.py adds /readyz, which returns 200 once intake has started and Redis answers PING. The management API, pages and report viewing are injected from the outer api/ package, and the HTTP infrastructure does not import it. GET /api/catalog only reads the catalog snapshot the runtime process saves in Redis; the queue process builds no execution graph. The report router returns only regular files of two fixed forms under a dedicated root, reading from the same verified descriptor; the queue process entry point api/__main__.py hides report paths and queries in uvicorn's access log. uvicorn runs on the queue process's event loop, and process.run_host owns the signals. The management contract, authentication, and adding and removing routes are collected in the FastAPI document.

The intake (integration/) only validates format, prunes by sender identity and publishes the raw event; it does not judge event content. A Connector (integration/connector.py) consists of a name plus at least one of webhook (a synchronous parse function without I/O that returns a raw EventRequest or a protocol response) and listener (start and stop of an always-on connection), and is registered by api/app.py. The token check, JSON object validation, status codes and publishing belong to the shared intake in integration/webhook, and no provider can bypass them: a token mismatch returns 401, a malformed request 422, an unconfirmed publish 503, and a confirmed XADD 202 with message_id. HTTP starts before the listeners, listeners start in registration order, and shutdown runs in reverse order.

The scheduled trigger Connector("schedule") has only a listener: one periodic task reads the PostgreSQL schedule table at most every 30 seconds (id, cron, timezone, payload), decides fire times by wall-clock time, and publishes EventRequest(provider="internal", external_id="schedule:<id>:<fire time>", payload=<row payload>). The next fire time is kept only in memory, and the queue never writes the table; times missed before startup, during shutdown or during sleep are not caught up, and fire times more than 60 seconds late are skipped. See Scheduling for the scheduled trigger rules. The same cycle also reads one-shot reservations from the reservation table (id, at, payload, created_at) and publishes EventRequest(provider="internal", external_id="reservation:<id>:<at in UTC>", payload=<row payload>) exactly once, only for an at that had not yet arrived when the row was first read; the two tables are read separately, and a read failure in one does not affect the other. Reservation rows are created by general's child agent reservation; when one fires, reservation_fire deletes the row and hands it to general to judge and reply. See Scheduling for the one-shot reservation rules.

GitHub's POST /webhook/github requires X-GitHub-Event and X-GitHub-Delivery and stores only the three allowed headers and the raw body; authentication headers never reach Redis. Discord's DiscordGateway runs the SDK on the queue process's event loop and reads the raw MESSAGE_CREATE, MESSAGE_REACTION_ADD, and MESSAGE_REACTION_REMOVE from the gateway frame. It publishes only messages sent by the owner, DISCORD_ALLOWED_USER_ID, that come from neither a bot nor a webhook, and only the owner's reactions, and resolves the session and parent session with the channel mapping table (the general channel gets no session); button operations by users other than the owner are rejected immediately, while the owner's are deferred first and the raw interaction is then published. Slack Socket Mode publishes only deliveries for the configured team and channel and ACKs to Slack only after a successful publish; the Events API answers url_verification with the challenge synchronously and does not publish it. The rules for each entry point are in Queue.

The runtime process does not route by provider. core/builtin/app.py injects QueueConsumer into the Runtime as the read source, and the Runtime hands every EventRequest to the dispatch agent (config.DISPATCH_AGENT, the version-owned agent/dispatch.py). The dispatch agent routes without an LLM, interprets events under Python control and delegates through call_agent: it passes every GitHub event to github, which chooses the child for PRs, CI failures, issue assignments and issue closes, and ignores deliveries that already succeeded and out-of-scope events. github also ends valid but unsupported events such as push and release, recording the reason. Ordinary Discord conversation goes to general, projects to project_qa and issue development to issue; issue channel creation and the confirmation buttons are fixed processing of general. Every accepted Discord message gets one acceptance reaction, whichever of these entrances receives it. dispatch replies to the original channel with general's success or failure result. The confirmation button sets ctx.authorization only when re-verification succeeds; an internal payload without agent_name is a derived request for automated development and goes to issue after the issue channel and development record are rechecked, and one with agent_name is a named run and goes to that declared child (§2). Raw Slack events are delegated to slack, which identifies direct mentions of the owner, reads the context and sends a summary to the existing Discord notification destination. When processing ends, the dispatch agent ACKs with ctx.ack(ctx.message_id), and events it does not run are ACKed the same way; the Runtime does not ACK.

The github agent reads a formal PR approval from a raw pull_request_review with review.state=approved. It validates a positive-integer review ID and a non-empty commit ID and sets them, together with the actor, in the webhook metadata of the Source arguments. pr_event sends the notification using the Source's current owner and open state, and saves the delivery success through a tool. The dispatch agent converts external JSON into the ctx.data the entry agent receives; BaseAgent's control contains no provider formats. Discord API operations are handled by DiscordApiTool and notification delivery by tools/discord/deliver. See Discord for the concrete contract and configuration. SlackApiTool limits Slack API reads to 5 allowed read endpoints and the channel specified by SLACK_CHANNEL_ID. slack_search, used by the consolidated research and by slack for mention summaries, searches the whole workspace read-only with the owner's user token. Contract §12 · Invariants when making changes

Changes to shared contracts keep the boundaries of sections 1–5, and changes to state and termination handling keep the boundaries of sections 7–9. When adding a concrete component, update its declaration and the lists in that version's agent/compose.py (AGENTS for agents, SOURCES for Sources; ENTRANCES contains only dispatch, and agents started by named runs are declared as children of dispatch), and add no outward dependency to the shared infrastructure. Agents run only through the version store: the Runtime obtains the entrance through the run handle, and call_agent obtains children by name from ctx.agents. The Host never imports or calls component modules: components reach the Host through its modules (a child request goes through publish_child in queue/child.py), and periodic component work runs as agents started from the schedule table; component changes are pushed to the component repository's main, checked by the pre-push hook, and adopted by the runtime's sync only when they load, and a change of the contract between the Host and versions is deployed first in a form the current components still load with, with the components pushed afterwards; locks and caches across versions stay in the components and are obtained through shared() / task_lock() / keyed_lock() in core/shared_state.py; a lock wraps only one operation inside a tool, and no agent is called while it is held. The intake only validates format, prunes by sender identity and publishes the raw event; the queue carries only EventRequest, and core does not route by provider or payload but hands everything to the dispatch agent, which also performs the ACK. Individual implementations never bypass call_agent as the only execution path for child agents, the distinction between tools and child agents, the shared Context, the LLM budget, or the mandatory evaluation of harnesses. I/O runs through await; the ORM in src/ uses only the async engine and AsyncSession, synchronous-only components go to asyncio.to_thread, and cancellation is never swallowed (checked by tests/entry/test_async_contracts.py, which also detects imports of the synchronous SQLAlchemy engine and session and calls to create_engine in src/).

Contract §13 · Verification

The regression targets are conversation execution and HTTP and page operations in the business test list, plus raw publishing by the queue and intake, the Host's child-request entry point (queue/child.py), Runtime execution, component versioning, the asyncio execution infrastructure and run log metering. Intake tests call the shared webhook intake and the Discord and Slack intake connections and check raw publishing, pruning and session attachment; conversation execution calls a single Runtime execution; HTTP is checked through TestClient and pages through Node.js. The version store is checked with small component trees and a mock VersionStore, and the git version store, startup from GitHub, sync, merge (rebase and push), the check CLI and the pre-push hook run against real git in temporary directories, with a bare repository standing in for GitHub and no network. Component code (agents, tools, skills, harnesses, Sources) lives in the component repository and is not a pytest target: it is checked by loading (check), and the quality of agent and tool decisions is handled by separate evaluation. External connections and real process starts are replaced by fixed responses (git in the versioning cases that use it is the only child process), and file output uses temporary areas. Transactions and compatibility of the ORM, DDL, migrations and a real DB, stream operations on a real Redis, the Host's concurrency control and restarts, a real GitHub, real LLM quality, and rendering in a real browser are outside this suite's guarantees.
